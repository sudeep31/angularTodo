1. Introduction — Why Patterns Matter

Patterns are proven, reusable solutions to recurring problems in software design. They are not copy-paste code — they are vocabulary and blueprints. For a front-end engineer working with Angular 21, patterns answer three questions:

QuestionPattern CategoryExample
How do I structure this object or service?Design Pattern (GoF)Factory, Singleton, Facade
How do I organise the application?Architectural PatternMFE, Atomic Design, NgRx
How do I make the right strategic decisions at scale?Architectural Strategy12-Factor, 6-Hour Design

2. Design Patterns — GoF & Front-End

The Gang of Four (GoF) catalogue defines 23 patterns across three categories. This section maps each relevant pattern to Angular 21, shows how it is implemented, and gives real-world examples.

2.1 Creational Patterns

Creational patterns deal with how objects are created, decoupling the creation logic from the consuming code.

Creational Factory Pattern

What it is: A function or class that creates objects without exposing instantiation logic to the caller.

How it helps: Centralises creation logic, makes swapping implementations easy, and removes new calls from consuming code.

// token-storage.factory.ts
export type StorageType = 'local' | 'session' | 'memory';

export interface TokenStorage {
  get(key: string): string | null;
  set(key: string, value: string): void;
  remove(key: string): void;
}

class LocalTokenStorage implements TokenStorage {
  get(key: string) { return localStorage.getItem(key); }
  set(key: string, value: string) { localStorage.setItem(key, value); }
  remove(key: string) { localStorage.removeItem(key); }
}

class MemoryTokenStorage implements TokenStorage {
  private store = new Map<string, string>();
  get(key: string) { return this.store.get(key) ?? null; }
  set(key: string, value: string) { this.store.set(key, value); }
  remove(key: string) { this.store.delete(key); }
}

export function createTokenStorage(type: StorageType): TokenStorage {
  switch (type) {
    case 'local':   return new LocalTokenStorage();
    case 'memory':  return new MemoryTokenStorage();
    default:        return new MemoryTokenStorage();
  }
}

export const TOKEN_STORAGE = new InjectionToken<TokenStorage>('TOKEN_STORAGE', {
  providedIn: 'root',
  factory: () => createTokenStorage(
    inject(PLATFORM_ID) === 'browser' ? 'local' : 'memory'
  ),
});
Code walkthrough — how this becomes the Factory Pattern:
  1. StorageType and TokenStorage interface — Define the contract first. Every storage class must implement get(), set(), and remove(). Callers will only ever see this interface — never a concrete class.
  2. LocalTokenStorage, MemoryTokenStorage — Concrete implementations, each wrapping a different mechanism. Crucially, none of these classes are exported. They are implementation details hidden inside the file.
  3. createTokenStorage(type) — this is the Factory function. It accepts a plain StorageType string and returns whichever concrete class matches. The caller never writes new LocalTokenStorage(). That decision lives in one place: the factory.
  4. TOKEN_STORAGE injection token — Angular's DI calls the factory automatically. It reads PLATFORM_ID to pick 'local' in the browser and 'memory' on the server (SSR). Any service that injects TOKEN_STORAGE gets the right implementation with no platform-detection code of its own.

Pattern conclusion: The interface hides the concrete types. The factory centralises all creation logic. Consumers depend on the TokenStorage abstraction — they never import or instantiate a storage class directly. Swapping the implementation means changing one line inside the factory — zero changes anywhere else.

Real-world use: Banking app — SSR uses in-memory storage, browser uses localStorage. The factory decides at runtime.

Creational Singleton Pattern

What it is: Ensures a class has only one instance and provides a global access point to it.

How it helps: Shared state (auth tokens, feature flags, app config) lives in one place.

// auth.service.ts — Angular-native singleton
@Injectable({ providedIn: 'root' })
export class AuthService {
  private readonly _user = signal<User | null>(null);
  readonly user = this._user.asReadonly();
  readonly isAuthenticated = computed(() => this._user() !== null);

  login(credentials: Credentials): Observable<void> {
    return this.http.post<AuthResponse>('/api/auth/login', credentials).pipe(
      tap(response => this._user.set(response.user))
    );
  }

  logout(): void {
    this._user.set(null);
  }
}
Code walkthrough — how this becomes the Singleton Pattern:
  1. @Injectable({ providedIn: 'root' }) — This single line is the Singleton declaration. Angular's DI container creates exactly one instance of AuthService for the entire application. Angular's injector is the Singleton registry — no static variables needed.
  2. private readonly _user = signal<User | null>(null) — A private writable signal. Only methods inside this class can change the user. This enforces controlled mutation — the core discipline of a Singleton.
  3. readonly user = this._user.asReadonly() — A public read-only projection. Consumers can read the current user but cannot call _user.set() from outside.
  4. readonly isAuthenticated = computed(...) — Derived state from the single source of truth. All consumers see the same value because they all reference the same instance.
  5. login() / logout() — The only mutation paths. Because every component injects the same object, calling logout() in the top nav immediately updates every other component reading isAuthenticated.

Pattern conclusion: providedIn: 'root' is Angular's native Singleton mechanism. Every component, service, and interceptor that injects AuthService receives the same object. There is no getInstance() — the DI container manages the lifecycle and guarantees uniqueness.

Anti-pattern warning: Do not implement the classic getInstance() static method in Angular. Let the DI container manage the singleton lifecycle.

Real-world use: AuthService, FeatureFlagService, AppConfigService.

Creational Builder Pattern

What it is: Separates the construction of a complex object from its representation, allowing step-by-step construction.

How it helps: Avoids constructor telescoping. Makes complex object creation readable and testable.

// http-request.builder.ts
export class HttpRequestBuilder<T> {
  private url = '';
  private params = new HttpParams();
  private headers = new HttpHeaders();

  withUrl(url: string): this { this.url = url; return this; }
  withParam(key: string, value: string): this {
    this.params = this.params.set(key, value);
    return this;
  }
  withBearerToken(token: string): this {
    this.headers = this.headers.set('Authorization', `Bearer ${token}`);
    return this;
  }
  build(): { url: string; options: object } {
    return { url: this.url, options: { params: this.params, headers: this.headers } };
  }
}

// Usage
const request = new HttpRequestBuilder<Transaction[]>()
  .withUrl('/api/transactions')
  .withParam('accountId', '12345')
  .withParam('pageSize', '50')
  .withBearerToken(inject(AuthService).token())
  .build();
Code walkthrough — how this becomes the Builder Pattern:
  1. Private fields (url, params, headers) — The parts of the product under construction. Private, not exposed until build() is called. Nobody outside the builder can see a half-assembled request.
  2. withUrl(), withParam(), withBearerToken() — Each method sets one property and returns this. Returning this is the Builder signature move — it enables method chaining.
  3. Method chaining is self-documenting — The call reads: "Build a request, set its URL, add two query params, attach a bearer token, then build." No positional arguments to misorder.
  4. build() — The terminal step. Assembles all accumulated parts into the final result object. You cannot use a half-built request because there is no result until build() is called.

Pattern conclusion: Without a builder you would pass 6 optional parameters to a function and struggle to remember which position is which. The builder names each step, makes construction legible, and enforces a build() gate so only complete objects are produced. Adding a new parameter (e.g. a timeout) means adding one withTimeout() method — no existing callers break.

Real-world use: Building paginated API requests, constructing chart config objects, assembling form field metadata.

2.2 Structural Patterns

Structural patterns deal with how objects and classes are composed to form larger structures.

Structural Facade Pattern

What it is: Provides a simplified interface to a complex subsystem of services, APIs, or libraries.

How it helps: Components talk to one facade instead of six services. The facade owns the orchestration complexity.

// account-facade.service.ts
@Injectable({ providedIn: 'root' })
export class AccountFacade {
  private readonly accountApi = inject(AccountApiService);
  private readonly transactionApi = inject(TransactionApiService);
  private readonly notificationService = inject(NotificationService);
  private readonly store = inject(Store);

  readonly accounts = toSignal(this.store.select(selectAllAccounts), { initialValue: [] });
  readonly isLoading = toSignal(this.store.select(selectAccountsLoading), { initialValue: false });

  loadDashboard(userId: string): void {
    this.store.dispatch(AccountActions.loadAccounts({ userId }));
  }

  async transferFunds(from: string, to: string, amount: number): Promise<void> {
    try {
      await firstValueFrom(this.accountApi.transfer({ from, to, amount }));
      this.notificationService.success(`Transferred £${amount}`);
    } catch {
      this.notificationService.error('Transfer failed — please retry');
    }
  }
}

// dashboard.component.ts — only knows about facade
@Component({ changeDetection: ChangeDetectionStrategy.OnPush })
export class DashboardComponent {
  protected readonly facade = inject(AccountFacade);
}
Code walkthrough — how this becomes the Facade Pattern:
  1. AccountFacade injects four dependencies — AccountApiService, TransactionApiService, NotificationService, and Store. These four are the complex subsystem. The facade is the single point that knows all of them.
  2. readonly accounts and readonly isLoading — Signals derived from the NgRx store. The component reads these without ever importing Store or knowing which selector drives them.
  3. loadDashboard(userId) — One method call dispatches an NgRx action. The component does not import AccountActions, does not know the action type, does not know the store exists.
  4. transferFunds() — Orchestrates three internal steps: API call, notification, and store reload. Error handling is centralised here. The component calls one method — the entire workflow is hidden.
  5. DashboardComponent — Injects only AccountFacade. If any underlying service changes its API, DashboardComponent is untouched.

Pattern conclusion: Instead of the component knowing about four services, it knows about one — the facade. The facade is the single point of contact. Refactoring an underlying service changes one file (the facade), not every component that uses it.

Real-world use: Banking dashboard facade, checkout facade, user profile facade.

Structural Adapter Pattern

What it is: Converts the interface of one class into another interface that clients expect.

How it helps: When integrating a third-party API that returns a different data shape, the adapter normalises it.

// legacy-account.adapter.ts
export interface LegacyAccountDto {
  acct_no: string;
  acct_type: string;
  bal: number;
  ccy: string;
}

export interface Account {
  id: string;
  type: 'current' | 'savings' | 'isa';
  balance: number;
  currency: string;
}

export function adaptLegacyAccount(dto: LegacyAccountDto): Account {
  return {
    id: dto.acct_no,
    type: mapAccountType(dto.acct_type),
    balance: dto.bal,
    currency: dto.ccy,
  };
}

@Injectable({ providedIn: 'root' })
export class AccountApiService {
  getAccounts(): Observable<Account[]> {
    return this.http.get<LegacyAccountDto[]>('/legacy/api/accounts').pipe(
      map(dtos => dtos.map(adaptLegacyAccount))
    );
  }
}
Code walkthrough — how this becomes the Adapter Pattern:
  1. LegacyAccountDto — The incompatible interface from the legacy API. Fields have cryptic names (acct_no, bal, ccy) and legacy type codes. You cannot change it — it is what the third-party system sends.
  2. Account — The target interface your Angular app expects. Clean, descriptive names. This is what all components, services, and state management code works with.
  3. adaptLegacyAccount(dto) — this is the Adapter. It takes the incompatible type and returns the target type. Each field mapping is explicit: dto.acct_no → id, dto.bal → balance, dto.ccy → currency.
  4. mapAccountType() — A helper that translates legacy string codes ('CA') to typed union values ('current'). The adapter does not just rename — it translates domain concepts.
  5. AccountApiService.getAccounts() — The HTTP response is LegacyAccountDto[] but the return type is Observable<Account[]>. The .pipe(map(...adaptLegacyAccount)) is the adapter firing at the boundary. The rest of the app never imports LegacyAccountDto.

Pattern conclusion: The legacy API and your application speak different "languages". The Adapter is the translator — all legacy complexity is contained in one file. When the legacy API changes its field names, you update one file, the adapter. Every component, service, and test in your application continues to work with the clean Account interface.

Real-world use: AngularJS → Angular 21 migration, integrating third-party payment SDKs, normalising multi-bank API responses.

Structural Decorator Pattern

What it is: Adds behaviour to an object dynamically without modifying its class.

How it helps: Cross-cutting concerns (logging, caching, retry) added without polluting business logic.

// cached-account-api.service.ts
@Injectable()
export class CachedAccountApiService extends AccountApiService {
  private readonly cache = new Map<string, { data: Account[]; timestamp: number }>();
  private readonly TTL = 60_000;

  override getAccounts(): Observable<Account[]> {
    const cached = this.cache.get('accounts');
    if (cached && Date.now() - cached.timestamp < this.TTL) {
      return of(cached.data);
    }
    return super.getAccounts().pipe(
      tap(data => this.cache.set('accounts', { data, timestamp: Date.now() }))
    );
  }
}

// app.config.ts
export const appConfig: ApplicationConfig = {
  providers: [
    { provide: AccountApiService, useClass: CachedAccountApiService },
  ],
};
Code walkthrough — how this becomes the Decorator Pattern:
  1. extends AccountApiService — The Decorator inherits from the class it wraps. CachedAccountApiService IS an AccountApiService (same interface, same method signatures). Consumers do not know they are talking to a wrapper.
  2. private readonly cache = new Map<...>() — Internal state the original class does not have. This is the added behaviour — the cache layer is entirely new, bolted on without touching the original class.
  3. override getAccounts() — Intercepts the call before it reaches the real implementation. override makes this explicit and catches typos at compile time.
  4. Cache hit check — If data exists and is fresh, returns of(cached.data) immediately. No HTTP request is made. The original service is bypassed entirely.
  5. super.getAccounts() — Cache miss: delegates to the original service. The real service does not know it is being wrapped.
  6. { provide: AccountApiService, useClass: CachedAccountApiService } — Angular's DI substitutes the decorator everywhere the original is injected. Zero changes in consuming code.

Pattern conclusion: The cache behaviour is added without modifying AccountApiService. The original class is unchanged and still testable on its own. Consumers are unaware of the wrapper. This is Decorator: new behaviour added by wrapping, not by modifying.

Real-world use: Caching HTTP responses, adding analytics tracking, wrapping API services with retry logic.

Structural Proxy Pattern — HTTP Interceptor

What it is: Provides a surrogate that controls access to another object, implementing the same interface.

How it helps: Lazy loading, access control, and HTTP interceptors all follow this pattern.

// auth.interceptor.ts
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const authService = inject(AuthService);
  const token = authService.token();

  if (!token) return next(req);

  const authorisedReq = req.clone({
    headers: req.headers.set('Authorization', `Bearer ${token}`),
  });

  return next(authorisedReq).pipe(
    catchError(error => {
      if (error.status === 401) authService.logout();
      return throwError(() => error);
    })
  );
};
Code walkthrough — how this becomes the Proxy Pattern:
  1. HttpInterceptorFn — Angular's functional interceptor sits in the HTTP pipeline, between the component and the server. Every outbound request passes through it — this is the Proxy position.
  2. inject(AuthService) and authService.token() — The proxy reads the token from the singleton service, handling this cross-cutting concern so that components never have to.
  3. if (!token) return next(req) — The proxy is transparent when there is nothing to do. Unauthenticated requests pass through unchanged. The component is not aware this check happened.
  4. req.clone({ headers: ... }) — HTTP requests are immutable. clone() creates a modified copy with the Authorization header injected. The component never modified the request — the proxy did.
  5. catchError(error => ...) — On a 401, the proxy calls authService.logout() and re-throws. The component that triggered the request does not need any 401-handling code — the proxy owns that responsibility.

Pattern conclusion: The component calls this.http.get('/api/accounts') as normal. It does not know a proxy exists. The interceptor — the Proxy — controls access to the HTTP resource: adding credentials on the way out and handling auth failures on the way back. This is exactly the Proxy pattern: a surrogate that controls and enriches access to another object.

Real-world use: Auth token injection, request/response logging, rate limiting, offline queue.

2.3 Behavioural Patterns

Behavioural patterns deal with communication and responsibility between objects.

Behavioural Observer Pattern — Signals

What it is: Defines a one-to-many dependency — when one object changes state, all dependents are notified automatically.

How it helps: Decouples publishers from subscribers. Components react to state changes without polling.

// notifications.service.ts
@Injectable({ providedIn: 'root' })
export class NotificationService {
  private readonly _messages = signal<Notification[]>([]);
  readonly messages = this._messages.asReadonly();
  readonly unreadCount = computed(() => this._messages().filter(m => !m.read).length);

  push(message: Notification): void {
    this._messages.update(msgs => [...msgs, message]);
  }
}

// notification-bell.component.ts — Observer
@Component({ changeDetection: ChangeDetectionStrategy.OnPush })
export class NotificationBellComponent {
  protected readonly count = inject(NotificationService).unreadCount;
  // Automatically re-renders when unreadCount changes
}
Code walkthrough — how this becomes the Observer Pattern:
  1. private readonly _messages = signal<Notification[]>([]) — The Subject (the Observable source). Holds the canonical list. private means only methods inside this service can change it.
  2. readonly messages = this._messages.asReadonly() — A read-only Observable view. Observers can read but cannot push new values directly.
  3. readonly unreadCount = computed(...) — A derived Observable. Automatically recalculates whenever _messages changes. Any component that reads unreadCount() is an implicit subscriber.
  4. push(message) — Calls update() on the signal. This is the notify step. The signal graph propagates the change — every computed value and template binding depending on _messages is re-evaluated automatically.
  5. NotificationBellComponent.count — Reads inject(NotificationService).unreadCount. There is no subscribe() call. When push() is called anywhere in the app, Angular re-renders this component. No manual subscription, no memory leak from forgetting to unsubscribe.

Pattern conclusion: _messages is the publisher. NotificationBellComponent (and any other component reading the signal) is the subscriber. The signal graph IS the Observer pattern: when the source changes, all dependents are notified automatically. Angular Signals eliminate the subscribe/unsubscribe boilerplate while preserving the pattern's intent.

Real-world use: Live transaction feeds, notification centres, real-time dashboard updates.

Behavioural Strategy Pattern

What it is: Defines a family of algorithms, encapsulates each one, and makes them interchangeable.

How it helps: Swap sorting, validation, or formatting logic at runtime without if/switch chains.

// transaction-sort.strategy.ts
export type SortStrategy = (a: Transaction, b: Transaction) => number;

export const sortByDateDesc: SortStrategy = (a, b) =>
  new Date(b.date).getTime() - new Date(a.date).getTime();
export const sortByAmountDesc: SortStrategy = (a, b) => b.amount - a.amount;

// transaction-list.component.ts
@Component({ changeDetection: ChangeDetectionStrategy.OnPush })
export class TransactionListComponent {
  private readonly transactions = inject(TransactionService).transactions;
  protected readonly sortKey = signal<'date' | 'amount'>('date');

  private readonly strategies = {
    date: sortByDateDesc,
    amount: sortByAmountDesc,
  };

  protected readonly sorted = computed(() =>
    [...this.transactions()].sort(this.strategies[this.sortKey()])
  );
}
Code walkthrough — how this becomes the Strategy Pattern:
  1. SortStrategy type — A function signature every strategy must satisfy. This is the strategy interface — the contract all algorithms share.
  2. sortByDateDesc, sortByAmountDesc — Two concrete strategies, each a pure function. They are interchangeable because they both satisfy SortStrategy. None know about the component or each other.
  3. sortKey = signal<'date' | 'amount'>('date') — The signal that determines which strategy is active at runtime. Changing this signal swaps the algorithm with no component rebuild.
  4. strategies: Record<string, SortStrategy> — A lookup map that links each key to a strategy function. Adding a new sort order means adding one entry to this map.
  5. sorted = computed(...) — Reads both sortKey and transactions. When either changes, it recomputes using whichever strategy is selected. The computed itself does not know which algorithm runs.

Pattern conclusion: The sorting algorithm is a variable — a first-class object selected at runtime. There is no if/else chain. Each algorithm is isolated and independently testable. Adding a new sort option does not touch existing code — this is the Open/Closed Principle, enabled by Strategy.

Real-world use: Sorting/filtering strategies, payment validation (sort code vs IBAN), export format strategies.

Behavioural Command Pattern

What it is: Encapsulates a request as an object, enabling parameterisation, queuing, logging, and undo/redo.

// command.interface.ts
export interface Command {
  execute(): void;
  undo(): void;
  description: string;
}

// command-history.service.ts
@Injectable({ providedIn: 'root' })
export class CommandHistoryService {
  private readonly _history = signal<Command[]>([]);
  readonly history = this._history.asReadonly();

  execute(command: Command): void {
    command.execute();
    this._history.update(h => [...h, command]);
  }

  undo(): void {
    const last = this._history()[this._history().length - 1];
    if (last) {
      last.undo();
      this._history.update(h => h.slice(0, -1));
    }
  }
}
Code walkthrough — how this becomes the Command Pattern:
  1. Command interface — Defines the contract: every command must have execute(), undo(), and a description. This is the Command abstraction — the history service only knows this interface.
  2. Constructor captures all data — api, store, from, to, amount are stored at creation time. The command is a self-contained operation object.
  3. description — A human-readable label, useful for audit logs and undo history UI ("Transfer £500 from 12345678 to 87654321").
  4. execute() — Performs the transfer via the API and refreshes the store. This is the forward operation.
  5. undo() — Performs a reverse transfer. This is the compensating operation — what makes this pattern powerful for financial UIs.
  6. CommandHistoryService.execute(command) — Runs the command and pushes it onto the history stack. The service does not know what the command does — it just calls command.execute() through the interface.
  7. undo() — Pops the last command and calls command.undo(). The service does not know the implementation — it only uses the Command interface.

Pattern conclusion: The transfer operation is encapsulated as an object with a known lifecycle: create → execute → optionally undo. The CommandHistoryService is the invoker. It can undo any command without knowing anything about banking logic. New commands (e.g. CreatePayeeCommand) are added by implementing Command — no history service code changes.

Real-world use: Transaction undo, form wizard step history, admin bulk-action queues.

Behavioural Mediator Pattern

What it is: Defines an object that encapsulates how a set of objects interact. Components communicate through the mediator rather than directly.

// dashboard-mediator.service.ts
@Injectable({ providedIn: 'root' })
export class DashboardMediatorService {
  private readonly _selectedAccount = signal<string | null>(null);
  readonly selectedAccount = this._selectedAccount.asReadonly();

  selectAccount(id: string): void {
    this._selectedAccount.set(id);
  }
}

// account-list.component.ts — publishes
export class AccountListComponent {
  private readonly mediator = inject(DashboardMediatorService);
  onSelect(id: string): void { this.mediator.selectAccount(id); }
}

// transaction-panel.component.ts — subscribes
export class TransactionPanelComponent {
  protected readonly accountId = inject(DashboardMediatorService).selectedAccount;
}
Code walkthrough — how this becomes the Mediator Pattern:
  1. _selectedAccount — A private writable signal. This is the shared communication channel — the Mediator's state. No component holds this state; it lives in the Mediator.
  2. readonly selectedAccount = this._selectedAccount.asReadonly() — Public read-only access. Components can subscribe to changes but cannot write directly.
  3. selectAccount(id) — A public write method. Any component calls this to announce "the user selected this account". The Mediator does not know — or care — which component called it.
  4. AccountListComponent — Injects the Mediator and calls mediator.selectAccount(id) on user click. It does not hold a reference to TransactionPanelComponent. It does not know which other components care about account selection.
  5. TransactionPanelComponent.accountId — Reads mediator.selectedAccount. When AccountListComponent calls selectAccount(), this signal updates and TransactionPanelComponent re-renders. The two components have never referenced each other.

Pattern conclusion: Without a Mediator, AccountListComponent would hold a reference to TransactionPanelComponent — tight coupling. With the Mediator, both components only know the Mediator service. Connection count reduces from n×n (components referencing each other) to n×1 (every component talks only to the Mediator). Adding a new panel means injecting the Mediator — zero changes to existing components.

Real-world use: Dashboard coordination, replaces complex chains of @Output() events between sibling components.

Behavioural State Pattern — Signal State Machine

What it is: Allows an object to alter its behaviour when its internal state changes.

// loan-application-state.ts
export type LoanState = 'idle' | 'personal-details' | 'income-check' | 'credit-check' | 'decision' | 'approved' | 'declined';

const TRANSITIONS: Record<LoanState, LoanState[]> = {
  'idle':             ['personal-details'],
  'personal-details': ['income-check'],
  'income-check':     ['credit-check'],
  'credit-check':     ['decision'],
  'decision':         ['approved', 'declined'],
  'approved':         [],
  'declined':         ['personal-details'],
};

@Injectable({ providedIn: 'root' })
export class LoanApplicationService {
  private readonly _state = signal<LoanState>('idle');
  readonly state = this._state.asReadonly();

  transition(to: LoanState): void {
    const allowed = TRANSITIONS[this._state()];
    if (!allowed.includes(to)) throw new Error(`Invalid: ${this._state()} → ${to}`);
    this._state.set(to);
  }
}
Code walkthrough — how this becomes the State Pattern:
  1. LoanState union type — Enumerates every possible state. These are the state nodes. The type system prevents any other string from being used.
  2. TRANSITIONS map — Defines which states can follow which. 'decision' can go to 'approved' or 'declined'. 'approved' has an empty array — no valid next state. Illegal transitions are structurally impossible.
  3. _state = signal<LoanState>('idle') — A single signal holds the current state. The entire machine's memory is this one value.
  4. canSubmit = computed(...) — A derived signal that changes behaviour based on state. The template reads canSubmit() — no if chains needed in the template.
  5. transition(to) — The guard function. It reads TRANSITIONS[current state] and throws if the requested transition is not allowed. Only valid transitions reach _state.set(to).

Pattern conclusion: The object's available actions change depending on _state. The TRANSITIONS map is a declarative replacement for complex if/switch logic. A developer reading the code immediately sees the full state graph. Adding a new state means one entry in LoanState and one row in TRANSITIONS — no existing transition logic changes.

Real-world use: Loan application wizard, KYC onboarding, checkout state machine.

Behavioural Chain of Responsibility — Validator Chain

What it is: Passes a request along a chain of handlers. Each handler decides to process it or pass it to the next.

// validator-chain.ts
export type ValidatorFn = (value: string) => string | null;

export function createValidatorChain(...validators: ValidatorFn[]): ValidatorFn {
  return (value: string): string | null => {
    for (const validator of validators) {
      const error = validator(value);
      if (error) return error;
    }
    return null;
  };
}

const required: ValidatorFn = v => v.trim() ? null : 'This field is required';
const minLength = (n: number): ValidatorFn => v =>
  v.length >= n ? null : `Minimum ${n} characters`;
const sortCode: ValidatorFn = v =>
  /^\d{2}-\d{2}-\d{2}$/.test(v) ? null : 'Format must be 00-00-00';

const validateSortCode = createValidatorChain(required, minLength(8), sortCode);
Code walkthrough — how this becomes the Chain of Responsibility Pattern:
  1. ValidatorFn type — Every handler in the chain must match this signature: takes a string, returns a string error or null. This is the handler interface — the chain does not care about implementation, only the contract.
  2. createValidatorChain(...validators) — The chain builder. Receives any number of handler functions and returns a new single function that runs them in sequence.
  3. for (const validator of validators) — Iterates through each handler in the order provided.
  4. if (error) return error — This is the chain-breaking behaviour. The first handler that finds a problem returns its error immediately. Remaining handlers do not run — matching the GoF intent.
  5. return null — If all handlers pass, the chain concludes with no error — the value is valid.
  6. requiredValidator, minLength(8), sortCode — Three concrete handlers, each responsible for exactly one rule. None knows about the others.
  7. createValidatorChain(required, minLength(8), sortCode) — Assembles the chain. Order matters: cheapest checks first, most specific last. Exactly like HTTP middleware ordering.

Pattern conclusion: Each validator is a single-responsibility handler. None knows about the others. The chain builder links them without any handler needing modification. Adding a new rule means passing it as an extra argument — existing validators are unchanged. This is Chain of Responsibility: a request (the field value) passes through a sequence of handlers until one handles it or all pass.

Real-world use: Form validation pipelines, Angular HTTP interceptor chain, middleware for auth → logging → error handling.

3.4 Saga Pattern

What it is: Manages long-running distributed transactions using a sequence of local transactions with compensating actions on failure. NgRx Effects implement this.

START └─► Create Account ├─ SUCCESS → Provision Card │ ├─ SUCCESS → Send Email → COMPLETE │ └─ FAIL → Close Account (compensate) → FAILED └─ FAIL → FAILED
// account-onboarding.effects.ts
startOnboarding$ = createEffect(() =>
  this.actions$.pipe(
    ofType(OnboardingActions.start),
    switchMap(({ customerId }) =>
      this.accountApi.createAccount(customerId).pipe(
        switchMap(account =>
          this.cardApi.provisionCard(account.id).pipe(
            switchMap(card =>
              this.emailApi.sendWelcome({ customerId, accountId: account.id }).pipe(
                map(() => OnboardingActions.complete({ account, card })),
                catchError(() => of(OnboardingActions.partialSuccess({ account, card })))
              )
            ),
            catchError(err =>
              this.accountApi.closeAccount(account.id).pipe(
                map(() => OnboardingActions.failed({ error: err.message }))
              )
            )
          )
        ),
        catchError(err => of(OnboardingActions.failed({ error: err.message })))
      )
    )
  )
);

Real-world use: Banking onboarding, loan disbursement, e-commerce checkout.

3.5 CQRS & Event Sourcing

CQRS: Separates read operations (queries) from write operations (commands). Event Sourcing: Stores the sequence of events that produced state rather than current state.

// COMMANDS (write side) — dispatched actions
store.dispatch(AccountActions.debit({ accountId, amount }));

// QUERIES (read side) — selectors
const balance = toSignal(store.select(selectAccountBalance(accountId)));

// Every state change is an event
type AccountEvent =
  | { type: 'CREDITED'; accountId: string; amount: number }
  | { type: 'DEBITED'; accountId: string; amount: number }

function replayAccount(events: AccountEvent[]): AccountState {
  return events.reduce(applyEvent, initialAccountState);
}

Real-world use: Financial ledgers, audit trails, undo history.

3.8 Feature-Sliced Design

What it is: Organises code by feature and layer, not by file type. Each feature is a vertical slice containing its own components, services, state, and API.

src/app/ ├── features/ │ ├── accounts/ │ │ ├── components/ (Smart + presentational) │ │ ├── services/ (AccountFacade, AccountApiService) │ │ ├── state/ (NgRx actions, reducers, effects, selectors) │ │ ├── models/ (Account interface, DTOs) │ │ └── accounts.routes.ts │ ├── transactions/ │ └── loans/ ├── shared/ │ ├── ui/ (Atomic design components) │ └── utils/ (Pure functions) └── core/ ├── interceptors/ └── app.config.ts
Rule: Features do not import from each other. They communicate through shared services or the store.

// Signal-based form — replaces AngularJS ngModel + $watch
@Component({
  selector: 'app-transfer-form',
  standalone: true,
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    <form (ngSubmit)="submit()">
      <label for="from">From Account</label>
      <input id="from" [value]="fromAccount()"
        (input)="fromAccount.set($any($event.target).value)" />
      @if (errors().fromAccount) {
        <p role="alert">{{ errors().fromAccount }}</p>
      }
      <label for="amount">Amount</label>
      <input id="amount" type="number" [value]="amount()"
        (input)="amount.set(+$any($event.target).value)" />
      @if (errors().amount) {
        <p role="alert">{{ errors().amount }}</p>
      }
      <button type="submit" [disabled]="!isValid()">Transfer</button>
    </form>
  `,
})
export class TransferFormComponent {
  protected readonly fromAccount = signal('');
  protected readonly amount = signal<number | null>(null);
  protected readonly errors = computed(() => ({
    fromAccount: !this.fromAccount().trim() ? 'Please select an account' : null,
    amount: (this.amount() ?? 0) <= 0 ? 'Amount must be greater than zero' : null,
  }));
  protected readonly isValid = computed(() =>
    Object.values(this.errors()).every((e) => e === null),
  );
  protected submit(): void { if (!this.isValid()) return; }
}
