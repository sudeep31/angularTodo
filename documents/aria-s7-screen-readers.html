7.1

Overview & Testing Setup

Screen readers do not simply "read out" attributes — each AT has its own virtual buffer model, announcement queue, and user mode. A feature that works perfectly in one combination may be completely broken in another. This reference documents tested behaviour across the five major AT products.

⚠️

Market share context (WebAIM Screen Reader Survey, 2024): JAWS (~46% primary use), NVDA (~30%), VoiceOver iOS (~11%), ZoomText (~5%), VoiceOver macOS (~9%), TalkBack (~7%), Narrator (~2%). Test at minimum: NVDA + Firefox, JAWS + Chrome, and VoiceOver + Safari.

Standard Test Browser Pairings

Screen Reader Primary Browser Platform Cost
NVDA (NonVisual Desktop Access) Firefox Windows Free, open source
JAWS (Job Access With Speech) Chrome or Edge Windows Commercial (free trial mode available)
VoiceOver Safari macOS, iOS, iPadOS Free — built into Apple OS
TalkBack Chrome Android Free — built into Android
Narrator Edge Windows 11 Free — built into Windows
7.2

NVDA + Firefox

NVDA (NonVisual Desktop Access)
Version 2024.4 + Firefox 127 — Windows 10/11
Desktop ~30% Market Share
NVDA is the most popular free screen reader. It has two primary modes: Browse mode (virtual cursor for reading the DOM) and Focus mode (passes keypresses to the page for form interaction). NVDA switches modes automatically; users can toggle with InsertSpace.

Primary navigation modes

Browse Mode (default) Focus Mode (forms)

Critical keyboard shortcuts

H — jump to next heading
B — jump to next button
L — jump to next list
G — jump to next graphic
T — jump to next table
F — jump to next form field
D — jump to next ARIA landmark
R — jump to next live region
Insert + Space — toggle Browse / Focus mode
Insert + F7 — list all headings / links / landmarks
Angular notes: NVDA reads aria-label and aria-labelledby reliably. Live regions work well with static DOM. Dynamic content injected by Angular signals (@if, @for) is picked up by the virtual buffer after a short delay. NVDA's Browse mode can escape aria-modal dialogs without [inert] on background elements.
7.3

JAWS + Chrome

JAWS (Job Access With Speech)
Version 2025 + Chrome 126 — Windows 10/11
Desktop ~46% Market Share
JAWS is the dominant commercial screen reader, particularly in enterprise and government contexts. It has extensive ARIA support and tends to be the most "correct" interpreter of the ARIA spec. It also has Virtual PC Cursor (browse mode) and PC Cursor (focus mode).

Primary navigation modes

Virtual PC Cursor (browse) PC Cursor (focus/forms) Application Mode (custom widgets)

Critical keyboard shortcuts

H — next heading | Shift+H — previous heading
B — next button | F — next form field
T — next table | G — next graphic
R — next live region | Insert+F11 — list landmarks
Insert+F6 — list headings | Insert+F7 — list links
Insert+Z — toggle Virtual Cursor on/off
Angular notes: JAWS handles Angular SPAs well when proper TitleStrategy announcements are in place. Role=application regions (widgets) switch JAWS to PC Cursor automatically when properly structured. JAWS reads aria-describedby content as a separate "description" announcement after the main label — leave a short pause in test scripts for this.
7.4

VoiceOver macOS + Safari

VoiceOver (macOS)
macOS 15 Sequoia + Safari 18
Desktop ~9% Market Share
VoiceOver on macOS navigates via the VoiceOver cursor (a distinct concept from keyboard focus). Users interact through VO (CtrlOption) + navigation keys. Web content uses Web Rotor for quick navigation by element type.

Critical keyboard shortcuts

VO + Right/Left — navigate DOM order
VO + U — open Web Rotor (headings, links, form controls, landmarks)
VO + Cmd + H — next heading
VO + Space — activate element (click)
VO + A — read from cursor position
VO + F3 — describe element under cursor
Ctrl — stop reading
Angular notes: VoiceOver on macOS is generally excellent with ARIA when using Safari. Chrome on macOS has historically worse ARIA support with VoiceOver — always test the Safari + VoiceOver pairing specifically. VoiceOver reads aria-live="assertive" reliably but may queue polite announcements differently from NVDA/JAWS.
7.5

VoiceOver iOS + Safari

VoiceOver (iOS / iPadOS)
iOS 18 / iPadOS 18 + Safari
Mobile ~11% Market Share
iOS VoiceOver uses swipe gestures to navigate. Swipe right moves to the next element; swipe left moves to the previous. Double-tap activates. Three-finger swipe scrolls. The Rotor (rotate two fingers) changes navigation granularity (headings, words, characters, links, form controls).

Critical gestures

Swipe right/left — next/previous element
Double-tap — activate element
Two-finger rotate — change Rotor setting
Two-finger double-tap — start/stop reading
Three-finger swipe up/down — scroll page
Three-finger double-tap — toggle VoiceOver mute
Angular notes: iOS VoiceOver has limited support for aria-live="assertive" — it often ignores assertive interruptions. Use polite for iOS-targeted announcements. Touch targets must be at minimum 44×44 CSS pixels (WCAG 2.5.5, AAA; WCAG 2.5.8, AA in 2.2). Angular CDK LiveAnnouncer works reliably on iOS Safari. Custom keyboard interactions (arrow keys, Home/End) are unavailable — touch-only navigation requires all content to be reachable via sequential swipe.
7.6

TalkBack + Chrome (Android)

TalkBack
Android 14 + Chrome for Android 126
Mobile ~7% Market Share
TalkBack is the built-in Android screen reader, similar to iOS VoiceOver in gesture model. Swipe right to navigate forward, swipe left for back. Double-tap to activate. Users can connect a Bluetooth keyboard for full keyboard navigation (same conventions as desktop screen readers).

Critical gestures

Swipe right/left — next/previous element
Double-tap — activate element
Swipe up then right — open TalkBack menu
Two-finger swipe down — read from top
Swipe up, down (reading controls) — change granularity
Angular notes: TalkBack ARIA support has improved substantially with Android 14 + Chrome. Live regions work reliably. role="alert" is announced immediately. ARIA patterns relying on keyboard arrow navigation require a hardware keyboard for Android TalkBack users — always provide alternative touch-accessible interaction paths. Ensure all interactive elements have explicit aria-label or aria-labelledby — TalkBack sometimes does not compute accessible names from child text in custom components.
7.7

Narrator + Edge (Windows 11)

Narrator
Windows 11 + Microsoft Edge 126
Desktop ~2% Market Share
Narrator is the built-in Windows screen reader. It has improved dramatically with Windows 11 but remains behind NVDA and JAWS in ARIA support. It works best with Microsoft Edge. Narrator uses Scan Mode (toggle with Caps LockSpace) for browsing the DOM.

Critical keyboard shortcuts

Caps Lock + Space — toggle Scan Mode (browse vs focus)
Caps Lock + →/← — next/previous item
H (in Scan Mode) — next heading
B (in Scan Mode) — next button
F (in Scan Mode) — next form field
T (in Scan Mode) — next table
Caps Lock + Enter — activate element
Angular notes: Narrator's ARIA support has gaps compared to NVDA/JAWS. Test Narrator as a secondary AT rather than primary. Live regions generally work; complex custom widgets (role="grid", comboboxes) may have reduced announcements. Narrator announces role and state changes less verbosely than NVDA/JAWS — simpler, more predictable for basic interactions.

7.9

Angular-Specific Screen Reader Gotchas

Issue Root Cause AT Affected Solution
Route navigation not announced Angular router updates DOM without browser page load — AT never knows the page changed All Implement A11yTitleStrategy with LiveAnnouncer — see Section 5.10
OnPush component changes not read AT reads DOM; Angular's OnPush only updates DOM after signal/input change triggers CD — usually fine, but complex effects may not trigger CD NVDA, JAWS Ensure effects that modify accessible text are inside the Angular change detection cycle (use signals, not external DOM manipulation)
@if live region silently broken Live region inserted at same time as its content — AT never registered the region All Keep live region element always in DOM; change only its text content (see Section 5.11)
SSR hydration ID mismatch Server renders different IDs for aria-labelledby/aria-describedby than client — relationship attributes break All Use Angular's inject(APP_ID) with counter for stable IDs; avoid random UUID in constructor
CDK overlay focus not trapped on iOS cdkTrapFocus uses DOM focus — VoiceOver cursor is independent VoiceOver iOS Add aria-modal="true" on dialog; set inert on background. VoiceOver respects aria-modal in iOS 17+
Signals update faster than AT can announce Rapidly changing signal (e.g., character counter on every keystroke) triggers live region faster than AT speech queue can empty NVDA, JAWS Debounce the live region update: use RxJS debounceTime(300) or setTimeout inside effect
Angular Material overlays and NVDA Browse Mode NVDA Browse Mode allows navigation outside aria-modal dialogs without background inert NVDA Angular Material CDK Dialog sets background aria-hidden automatically. Custom dialogs must do this manually
[attr.aria-*] binding returns null — removes attribute Binding evaluates to null or undefined — Angular removes the attribute entirely, which changes the accessible name or state All Use explicit ternary: [attr.aria-invalid]="isInvalid ? 'true' : null". Removing is fine when the attribute should not exist; ensure the logic is intentional
✅

Minimum viable AT testing setup for Angular development: Install NVDA (free) and test with Firefox as part of every PR that touches accessible names, ARIA states, live regions, or focus management. Run automated axe-core scans (@axe-core/playwright or @axe-core/angular) as a CI gate. Test VoiceOver + Safari for every release candidate. Test TalkBack manually for any mobile-targeted features.
