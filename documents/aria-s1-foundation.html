1.1

What is ARIA?

ARIA stands for Accessible Rich Internet Applications. It is a set of HTML attributes defined by the W3C in the WAI-ARIA 1.2 specification (W3C Recommendation, June 2023). The current working draft of WAI-ARIA 1.3 was published in early 2025 and adds refinements but does not yet change the core attribute set used in production.

ARIA gives you three superpowers over native HTML:

🎭

Roles

Tell assistive technology what an element is — a button, a dialog, a tab, a live region. Example: role="dialog".

🏷️

Properties

Describe relationships and metadata — the label of an element, what it is described by, whether it is required. These are mostly static. Example: aria-label, aria-describedby.

🔀

States

Communicate current condition — whether a checkbox is checked, a menu is expanded, an input is invalid. These change dynamically. Example: aria-expanded, aria-checked.

⚠️

The First Rule of ARIA: Do not use ARIA if a native HTML element or attribute provides the same semantics. A <button> already has role="button", keyboard operability, and state management built in. ARIA only adds meaning — it never changes visual appearance or behaviour. Misused ARIA creates worse experiences than no ARIA at all.

1.2

The Accessibility Tree: The Bridge Between HTML and Screen Readers

When a browser loads an HTML page, it builds two parallel structures from the same markup:

  • The DOM Tree — the full HTML structure, used for rendering and JavaScript
  • The Accessibility Tree — a filtered, enriched version exposed to assistive technologies (screen readers, braille displays, voice control)

The accessibility tree strips out purely visual information (CSS, layout) and adds semantic meaning from HTML tags and ARIA attributes. Screen readers like NVDA, JAWS, and VoiceOver do not see your HTML directly — they read the accessibility tree through platform APIs (Windows: UI Automation / IAccessible2, macOS: NSAccessibility, Linux: AT-SPI2).

Here is how the same HTML is represented in the accessibility tree — notice what is kept, what is enriched, and what is hidden:

🔴 HTML in the DOM 
<div class="todo-app">
  <div class="header">
    <div class="icon">✓</div>
    My Todos
  </div>
  <div class="list">
    <div class="item">
      <div class="check"></div>
      Buy groceries
      <div class="del">×</div>
    </div>
  </div>
</div>
🔴 Accessibility Tree (div soup) 
generic "todo-app"
  generic "header"
    generic "✓"       ← meaningless
    text "My Todos"
  generic "list"
    generic "item"
      generic ""       ← invisible
      text "Buy groceries"
      generic "×"       ← meaningless

Screen reader reads:
"My Todos Buy groceries"
(no roles, no actions, no context)
✅ Semantic HTML in the DOM 
<main aria-label="Todo app">
  <h1>My Todos</h1>
  <ul role="list" aria-label="Todo items">
    <li>
      <input type="checkbox"
        id="t1"
        aria-label="Buy groceries,
                    mark complete" />
      <label for="t1">Buy groceries</label>
      <button
        aria-label="Delete: Buy groceries">
        <svg aria-hidden="true">...</svg>
      </button>
    </li>
  </ul>
</main>
✅ Accessibility Tree (semantic) 
main "Todo app"
  heading level=1 "My Todos"
  list "Todo items"
    listitem
      checkbox "Buy groceries,
                mark complete"
              checked=false
      button "Delete: Buy groceries"

Screen reader reads (on Tab):
"Buy groceries, mark complete,
 checkbox, unchecked"
(then Tab)
"Delete: Buy groceries, button"
💡

Inspect the accessibility tree yourself: In Chrome DevTools → Elements panel → select an element → Accessibility tab → toggle "Enable full-page accessibility tree" to see exactly what a screen reader receives. Firefox has an equivalent under Tools → Web Developer → Accessibility.

1.3

How ARIA Attributes Flow to Screen Readers (the pipeline)

Understanding this pipeline explains why some ARIA changes work instantly while others require specific patterns to be announced:

  1. You write HTML + ARIA — e.g. <div role="alert">Error: name is required</div>
  2. Browser builds the accessibility tree — the div is given role=alert, name="Error: name is required", and marked as a live region.
  3. Browser fires an accessibility event — on Linux this is an AT-SPI2 event; on Windows a UI Automation or IAccessible2 event; on macOS an NSAccessibility notification.
  4. Screen reader receives the event — NVDA, JAWS, or VoiceOver intercepts it via the platform accessibility API.
  5. Screen reader queues the announcement — polite regions wait for silence; assertive regions interrupt immediately.
  6. Speech engine speaks — the user hears: "Error: name is required, alert."
Your HTML + ARIA attributes
↓ Browser parses markup
↓ Accessibility Tree built (role · name · state · value)
↓ Platform Accessibility API event fired
Windows: UI Automation (UIA) · IAccessible2
macOS/iOS: NSAccessibility
Linux: AT-SPI2
Android: AccessibilityNodeInfo
↓ Screen reader intercepts event
NVDA · JAWS · VoiceOver · TalkBack · Narrator
↓ Speech queue updated (polite / assertive)
↓ User hears the announcement
⚠️

Critical Angular timing issue: if you set an aria-live region's text content in the same render cycle as the region is inserted into the DOM, many screen readers miss the announcement because they were not watching the region yet. Always pre-render the region in the initial HTML (empty), then update its content. Angular CDK's LiveAnnouncer handles this correctly — it is the safe default.

1.4

The Four Core Concepts: Name · Role · State · Value

Every interactive element in the accessibility tree is described by four fundamental properties. A screen reader uses all four when announcing an element to the user. Understanding this model makes every ARIA decision obvious.

Concept What it answers How it is set Screen reader announces
Name
(Accessible Name)		 "What is this thing called?" <label> text · aria-label · aria-labelledby · element text content · alt Read first: "Buy groceries"
Role "What kind of thing is this?" Native element (<button>, <input>) · role="…" attribute Read second: "…checkbox"
State "What condition is it in right now?" checked · disabled · aria-expanded · aria-selected · aria-pressed Read third: "…unchecked"
Value "What is its current value?" (for range/input elements) value attribute · aria-valuenow · aria-valuetext Read as part of name: "Volume, 60%"

When you focus the checkbox from our todo example, NVDA reads:

NVDA + Firefox — Focus on todo checkbox
[Tab key pressed]
"Buy groceries" … "checkbox" … "not checked"

[Space key pressed — toggles checkbox]
"checked"
🚫

If the accessible name is missing (no label, no aria-label, no text content), the screen reader announces just the role and state — leaving the user with "checkbox, not checked" and no idea what it represents.

1.5

Accessible Name Computation: How the Browser Calculates the Name

The browser uses the Accessible Name and Description Computation (ANDC) algorithm (W3C spec, accname-1.2) to derive the accessible name from multiple possible sources. The algorithm checks sources in priority order — the first match wins:

Priority Source Example Best used for
1 (highest) aria-labelledby aria-labelledby="title-id desc-id" Reusing existing visible text as a label
2 aria-label aria-label="Delete: Buy groceries" Icon buttons, elements with no visible text
3 Native label mechanism <label for="id"> · alt="" · <caption> Form controls — always prefer this
4 Element's text content <button>Save</button> Buttons, links with visible text
5 title attribute title="Download PDF" Fallback only — avoid relying on it
6 (lowest) placeholder placeholder="Search…" Never use as the only label — not persistent
🚫

Never use placeholder as the sole label for a form input. Placeholder text disappears when the user starts typing, leaving no label visible or accessible. It also fails WCAG 1.3.5 (Identify Input Purpose) and creates cognitive load for users with memory impairments. Always pair it with a <label>.

Worked Example — Angular Template

HTML — Angular Template 
<!-- EXAMPLE 1: aria-labelledby (priority 1)
     Concatenates text of #dialog-title AND #action-type
     Result → "Confirm Delete" -->
<h2 id="dialog-title">Confirm</h2>
<span id="action-type">Delete</span>
<button aria-labelledby="dialog-title action-type">
  Yes</button>
<!-- Screen reader: "Confirm Delete, button" (NOT "Yes") -->

<!-- EXAMPLE 2: aria-label (priority 2)
     Overrides visible text "×".
     Result → "Delete todo: Buy groceries" -->
<button
  [attr.aria-label]="'Delete todo: ' + todo().title">
  <span aria-hidden="true">×</span>
</button>
<!-- Screen reader: "Delete todo: Buy groceries, button" -->

<!-- EXAMPLE 3: <label for> (priority 3) — best for form inputs -->
<label for="todo-title">Todo title</label>
<input id="todo-title" type="text" />
<!-- Screen reader: "Todo title, edit text" -->

<!-- EXAMPLE 4: Text content (priority 4) -->
<button>Save Changes</button>
<!-- Screen reader: "Save Changes, button" -->

<!-- EXAMPLE 5 — WRONG: no name source at all -->
<button>
  <svg aria-hidden="true">...</svg>
</button>
<!-- Screen reader: "button" — no name, user is lost -->
1.6

Hiding Content: aria-hidden, display:none, and .sr-only

One of the most common accessibility mistakes is misunderstanding which CSS or ARIA attribute hides content from which audience. Here is the definitive table:

Technique Hidden visually? Hidden from AT / screen reader? Focusable? Use for
display: none ✅ Yes ✅ Yes (removed from tree) ❌ No Conditionally hidden UI (modals when closed, @if blocks)
visibility: hidden ✅ Yes ✅ Yes (removed from tree) ❌ No Hiding without collapsing layout space
hidden attribute ✅ Yes ✅ Yes ❌ No Same as display:none — semantic HTML hide
aria-hidden="true" ❌ No (still visible) ✅ Yes (removed from AT tree) ⚠️ Still focusable! (dangerous) Decorative icons, duplicated text, visual-only flourishes
.sr-only (CSS class) ✅ Yes (1×1px clip) ❌ No (still in AT tree) ✅ Yes (can receive focus) Skip links, extra context for AT users, live region containers
opacity: 0 ✅ Yes ❌ No (still in AT tree) ✅ Yes Animated transitions — not for permanent hiding
🚫

Never put aria-hidden="true" on an element that can receive focus (a button, link, input, or element with tabindex). Screen reader users can still Tab to it — but when they get there, the screen reader announces nothing. This is called a ghost focus and is one of the most confusing experiences for blind users.

The .sr-only CSS Pattern — Correct Implementation

CSS — styles.css (global) 
/*
  .sr-only — Visually hidden but accessible to screen readers.
  Uses clip-path instead of clip (deprecated).
  NEVER use display:none or visibility:hidden here.
  The negative margin prevents it from affecting page flow.
*/
.sr-only {
  position: absolute;
  width: 1px;
  height: 1px;
  padding: 0;
  margin: -1px;
  overflow: hidden;
  clip-path: inset(50%);
  white-space: nowrap;
  border-width: 0;
}

/* Reveals on focus — for skip links */
.sr-only:focus {
  position: static;
  width: auto;
  height: auto;
  padding: inherit;
  margin: inherit;
  overflow: visible;
  clip-path: none;
  white-space: normal;
}

In Angular: Use Tailwind's Built-in sr-only Utility

HTML — Angular template with Tailwind sr-only 
<!-- Skip link: hidden until Tab is pressed -->
<a
  href="#main-content"
  class="sr-only focus:not-sr-only
         focus:absolute focus:top-2 focus:left-2 focus:z-50
         focus:bg-indigo-600 focus:text-white focus:px-4 focus:py-2
         focus:rounded focus:ring-2 focus:ring-white">
  Skip to main content
</a>

<!-- Extra context for screen readers on an icon button -->
<button type="button">
  <svg aria-hidden="true" focusable="false">...</svg>
  <span class="sr-only">Delete todo: Buy groceries</span>
</button>
<!-- Screen reader: "Delete todo: Buy groceries, button" -->

<!-- Live region container: pre-rendered empty,
     Angular signal updates populate it -->
<div
  aria-live="polite"
  aria-atomic="true"
  class="sr-only">
  {{ statusAnnouncement() }}
</div>

Categories of ARIA Attributes at a Glance

WAI-ARIA 1.2 defines 69 states and properties and 82 roles. They fall into clear categories. This overview sets the map — each category gets its own dedicated section in this guide.

Category Purpose Key attributes Guide section
Landmark Roles Page regions — let users jump between sections banner · main · navigation · complementary · contentinfo · search · form · region Section 2
Widget Roles Interactive controls the browser does not natively provide button · checkbox · combobox · dialog · grid · listbox · menu · slider · tab · tooltip · tree Section 2
Document Structure Roles Content structure and relationships article · definition · heading · img · list · listitem · note · presentation · none Section 2
Naming Properties Provide the accessible name or description aria-label · aria-labelledby · aria-describedby · aria-description (new in 1.3) Section 3
Relationship Properties Link elements to each other aria-controls · aria-owns · aria-flowto · aria-errormessage · aria-details Section 3
Widget Properties Configure widget behaviour aria-required · aria-readonly · aria-multiselectable · aria-orientation · aria-haspopup · aria-modal Section 3

1.8

The Five Golden Rules Before Writing Any ARIA

Before reaching for an aria- attribute, run through these rules in order. They prevent the vast majority of ARIA bugs seen in production Angular apps.

  • Rule 1 — Use native HTML first. <button> over <div role="button">, <input type="checkbox"> over <div role="checkbox">. Native elements come with role, keyboard support, focus management, and state — ARIA only gives you the role announcement, nothing else.
  • Rule 2 — Do not change native semantics. Never write <h2 role="tab"> — heading semantics and tab semantics conflict. If you need a tab, wrap the heading or use a different element.
  • Rule 3 — All interactive ARIA widgets must be keyboard operable. Adding role="button" to a div does not add keyboard support. You must also add tabindex="0" and handle keydown for Enter and Space. Angular CDK handles this — prefer it over manual implementation.
  • Rule 4 — Do not hide focusable elements with aria-hidden. If an element can receive Tab focus, it must be in the accessibility tree. Use display:none or the inert attribute instead if you want to remove it from both the visual and AT trees.
  • Rule 5 — All interactive elements must have an accessible name. Every button, link, form field, and landmark must have a name. Run your component through axe-core — a missing name is an automatic WCAG failure.
