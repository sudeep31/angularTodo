What is Web Accessibility (A11y)?

Web Accessibility — abbreviated A11y (11 letters between "A" and "y") — is the practice of designing and building digital products so that people with disabilities can perceive, understand, navigate, and interact with them equally.

It covers a broad spectrum of human ability:

👁️

Visual

Blindness, low vision, colour blindness — relying on screen readers, Braille displays, high-contrast modes.

👂

Auditory

Deafness and hard-of-hearing users needing captions, transcripts, and visual alerts.

🖐️

Motor

Users who rely on keyboards, switch access, voice control, or eye-tracking instead of a mouse.

🧠

Cognitive

Dyslexia, ADHD, autism — needing clear language, predictable layout, and reduced distraction.

🗣️

Speech

Non-verbal or speech-impaired users needing AAC device support and alternatives to voice input.

⚡

Situational

Temporary impairments — broken arm, bright sunlight, loud environment — benefiting everyone.

💡

Universal Design principle: Accessibility improvements almost always benefit all users — faster keyboard navigation, clearer copy, better colour contrast for bright-light conditions, and improved SEO are side-effects of building accessibly.

2

WCAG 2.1 — The Four Principles (POUR)

The Web Content Accessibility Guidelines (WCAG) 2.1, published by the W3C in June 2018, define 78 success criteria organised under four foundational principles — remembered as POUR.

P1

Perceivable

All information and UI components must be presentable in ways users can perceive.

  • Text alternatives for non-text content
  • Captions and audio descriptions
  • Content adaptable to different presentations
  • Distinguishable — colour, contrast, audio control
P2

Operable

UI components and navigation must be operable by every user.

  • Keyboard accessible — no keyboard traps
  • Enough time to read and use content
  • No content that causes seizures or reactions
  • Navigable with focus order and headings
P3

Understandable

Information and operation of the UI must be understandable.

  • Readable — language identified
  • Predictable — consistent navigation
  • Input assistance — error prevention and correction
P4

Robust

Content must be robust enough for current and future assistive technologies.

  • Valid, well-formed HTML
  • Name, Role, Value for all UI components
  • Status messages programmatically determined
3

Conformance Levels

Level Description Legal / Industry Status Example Criteria
A Minimum baseline. Failing these makes content inaccessible for some users. Required by most laws (ADA, EN 301 549) Non-text content has alt text; no keyboard traps
AA Standard target for public-facing products. Addresses major barriers. Industry standard; legally required in many jurisdictions 4.5:1 contrast ratio; live captions; error suggestions
AAA Enhanced support, not achievable for all content types. Recommended for specialist services (govt, health) 7:1 contrast; sign language; no timing at all
🎯

Target AA conformance as your baseline for every Angular application. It is the legal threshold in the EU (EN 301 549), UK (PSBAR 2018), US (Section 508), Australia (DDA), and Canada (AODA).

The Numbers

🌍

1.3 Billion People

Live with some form of disability globally — 16% of the world's population (WHO, 2023).

💰

$13 Trillion Market

The annual disposable income of people with disabilities and their families globally.

⚖️

Web accessibility lawsuits exceeded 4,600 in the US alone in 2023, up 300% since 2018.

🔍

SEO Boost

Semantic HTML, alt text, and heading structures directly improve search engine ranking.

Business & Engineering Benefits

  • Reduces legal exposure under ADA, AODA, EN 301 549, Section 508 and equivalent laws
  • Improves Core Web Vitals and Lighthouse scores — indirectly boosting SEO
  • Semantic HTML is easier to unit test and maintain
  • Keyboard-accessible components work better with test automation (Cypress, Playwright)
  • High-contrast and resizable UI gracefully handles mobile / unusual viewports

  • Demonstrates corporate social responsibility, improving brand reputation
⚠️

Retrofitting is expensive. The cost of fixing accessibility issues post-release is estimated at 30–100× the cost of building accessibly from the start. Treat A11y as a first-class requirement, not an audit afterthought.

Implementing A11y in Angular 21

5.1 — Semantic HTML First

Angular renders to the DOM — so semantic HTML is the foundation. Never replace native elements with divs when a semantic alternative exists.

HTML — Good vs Bad 
<!-- ✗ WRONG — div soup, no semantics -->
<div class="header">
  <div class="nav">
    <div (click)="navigate()">Home</div>
  </div>
</div>

<!-- ✓ CORRECT — semantic landmarks -->
<header role="banner">
  <nav aria-label="Primary navigation">
    <ul role="list">
      <li><a routerLink="/" routerLinkActive="active"
          [attr.aria-current]="isActive ? 'page' : null">Home</a></li>
    </ul>
  </nav>
</header>
<main id="main-content">...</main>
<footer role="contentinfo">...</footer>

5.1b — Semantic HTML Elements: When, How & Why

Every HTML element carries an implicit ARIA role. Choosing the right element gives you accessible semantics for free — without a single line of ARIA. Below is a complete reference for every element that matters for accessibility.

Landmark Elements — Page Structure

Landmarks let screen reader users jump directly between major page regions using a shortcut key (NVDA: R, JAWS: R, VoiceOver: W). A well-landmarked page is like a table of contents for AT users.

Element Implicit Role When to Use How to Use Why It Matters
<header> banner (when top-level) Site-wide header: logo, primary nav, site name. Once per page at top level. <header role="banner"> at the top of <body>. When inside <article> or <section>, it is generic — add role="banner" explicitly if needed. AT announces "banner landmark" so users can skip to or past the header quickly. Without it, keyboard users must Tab through every navigation link on every page load.
<nav> navigation Groups of navigation links — primary nav, breadcrumb, pagination, sidebar nav. Use multiple <nav>s per page when distinct navigation sets exist. Always add aria-label to distinguish multiple navs: <nav aria-label="Primary navigation">, <nav aria-label="Breadcrumb">. Use <ul> inside for a list of links. Screen readers list all navigation landmarks so users can jump directly to the one they need. Without labels, two <nav> landmarks are indistinguishable and announced as "navigation, navigation".
<main> main The primary content of the page — everything that is unique to this page (not shared chrome). Exactly one per page. <main id="main-content">. The id is the skip-link target. Add tabindex="-1" to make it programmatically focusable for focus management after route change. The skip-link target. Without <main>, keyboard users must Tab through the entire header and navigation every time they arrive on a page. Violates WCAG 2.4.1 (Bypass Blocks, Level A).
<section> region (only when labeled) A distinct thematic grouping of content that would appear in a document outline — e.g., "Features", "Testimonials", "Filter panel". Do not use it as a generic <div> replacement. Always provide a label: <section aria-labelledby="section-heading-id">. If you cannot provide a label, use <div> instead. Without a label, <section> has no ARIA role. Labeled sections become "region" landmarks that AT users can navigate to by name. Unlabeled sections are treated as generic divs by AT — the element adds nothing without a label.
<article> article Self-contained, independently distributable content: blog post, news article, product card, forum post, comment, widget. The content must make sense on its own if extracted from the page. Each article should have a heading that names it. Nest articles inside each other for comment threads (reply articles inside post article). No aria-label needed — the heading names it. AT announces "article" and users can navigate between articles on the page. Tells search engines and AT that the content is self-contained and shareable.
<aside> complementary Content tangentially related to the surrounding content: sidebars, pull quotes, advertising, related links, glossary panels. The content is supplementary — the main content still makes sense without it. <aside aria-label="Related articles">. If multiple asides exist on one page, label each one to distinguish them. AT users can choose to skip complementary content entirely using landmark navigation. Without it, sidebar content is indistinguishable from main content in the AT's linear reading order.
<footer> contentinfo (when top-level) Site-wide footer: copyright, links to legal pages, contact info, social media. Also used inside <article> for article metadata (author, date) — in that context it is generic, not contentinfo. <footer role="contentinfo"> at bottom of <body>. Add role="contentinfo" explicitly for clarity, though modern browsers infer it automatically for top-level <footer>. AT announces "contentinfo landmark" — users who want the copyright or privacy policy can jump directly to it. Without it, the footer is anonymous content that users must scroll all the way to.

Heading Elements — Document Outline

Element When to Use How to Use Why It Matters
<h1> The primary title of the page — one per page. In a SPA, update it on every route change. Matches or closely mirrors the <title> element content. In Angular: set via the route title property and reflect it as <h1> in the component template. Screen reader users often navigate by headings (NVDA: H, VoiceOver: Ctrl+Opt+Cmd+H). <h1> tells them "you are on the page about X." Without it, the page has no clear identity for AT.
<h2>–<h6> Sub-sections of the page in strict descending order: <h2> are top-level sub-sections, <h3> are sub-sub-sections, etc. Never skip levels (e.g., jumping from <h2> to <h4>). Choose level by document hierarchy, not by visual size. If you need a visually larger heading at a lower level, use CSS. In Angular: every <section aria-labelledby="id"> should have a corresponding <h2> or <h3> with that id. AT users build a mental map of the page from the heading structure. Skipped levels break the outline — "why is there an <h4> with no parent <h3>?" — and confuse navigation. HeadingsMap browser extension shows the outline.
⚠️

Never use headings for visual styling. Do not use <h3> because it looks the right size — use it because the content is a sub-section of an <h2>. Equally, do not skip a level because you want a smaller visual heading. Style with CSS; structure with the correct level.

Interactive Elements — Buttons, Links & Forms

Element When to Use How to Use Why It Matters / Common Mistake
<button> Any action that does not navigate to a new URL: submit form, delete item, toggle menu, open modal, increment counter. If clicking it changes something on-page — use a button. Always set type="button" (prevents accidental form submission). Add aria-label when the visible text alone is insufficient: aria-label="Delete todo: Buy groceries". For icon-only buttons, aria-label is mandatory. Native <button> is keyboard focusable, activatable with Enter and Space, announces "button" role to AT, and supports disabled natively. A <div (click)="..."> has none of these — it is inaccessible by default and requires manual ARIA, tabindex, and keyboard handlers to approximate the same behaviour.
<a href> Any navigation: links to another page, another URL, an anchor on the same page, a file download. If clicking it changes the URL or location — use a link. Always provide meaningful link text — never "click here" or "read more". For ambiguous links in repeated contexts, add aria-label: aria-label="Read more about Angular accessibility". Use rel="noopener noreferrer" for external links. In Angular, use routerLink for internal navigation. Links are announced as "link" by AT (not "button"). Keyboard: Enter activates a link; Space does not. Screen reader users can list all links on a page using a shortcut — vague link text like "click here" makes this list useless. WCAG 2.4.6 requires descriptive labels.
<label> Every <input>, <select>, and <textarea> on every form — no exceptions. The label describes what the field expects. Use explicit association via for/id: <label for="email">Email address</label> <input id="email" ...>. Never use placeholder as the only label — placeholder disappears when the user types and has insufficient contrast. Do not use aria-label on the input as a substitute for a visible label. Without a <label>, screen readers announce the input as just "edit text" — users do not know what to type. Clicking the label focuses the associated input (larger click target for motor-impaired users). WCAG 1.3.1 (Info and Relationships, Level A) requires this association.
<input type="..."> Any user-entered data. Choose the most specific type for the data: email, tel, number, date, url, search, password. Never use type="text" for data that has a semantic type. Always pair with <label>. Set autocomplete for user personal data (WCAG 1.3.5). Set inputmode for mobile keyboard type. For validation: add aria-required="true" and [attr.aria-invalid]="control.invalid && control.touched". Specific input types trigger the correct mobile keyboard (numeric keypad for tel), activate browser autofill, and help AT contextualise the field. type="email" tells AT "this field expects an email address" even before the user reads the label.
<select> Choosing one option from a list of 5–15 options where all options can be shown. Below 5 options: consider radio buttons. Above 15: consider a searchable combobox (ARIA pattern). Always associate with <label>. Use <optgroup label="..."> to group related options. Add a non-selectable first option as a placeholder: <option value="" disabled selected>Choose a status</option>. Native <select> has full keyboard support (↑/↓ to navigate options), AT announces the selected value, and it works across all platforms without ARIA. Custom dropdowns built from <div>s require the entire ARIA combobox or listbox pattern to reach the same baseline.
<fieldset> + <legend> Grouping related form controls that share a common purpose: a set of radio buttons, a group of checkboxes, billing address vs shipping address fields. The legend titles the group. <fieldset><legend>Filter todos by status</legend> ... </fieldset>. Angular alternative: <div role="group" aria-labelledby="group-label-id"> when you cannot use <fieldset> for styling reasons. Without grouping, radio buttons are announced individually: "All, radio button"; "Active, radio button" — with no context about what they represent. With <fieldset><legend>, AT announces: "Filter todos by status group: All, radio button" — the group name is always in context. WCAG 1.3.1 requires this for related controls.

Content & Media Elements

Element When to Use How to Use Why It Matters
<img> All images. The alt attribute is mandatory in HTML5 — its value depends on whether the image is informative, functional, decorative, or text. Informative: alt="Graph showing todo completion rising 40%"
Decorative: alt="" aria-hidden="true"
Functional (button icon): alt="Delete" (button has no other label)
Text image: alt="exact text shown in image" 		Screen readers read alt text in place of the image. Missing alt causes AT to announce the full file path ("img/logo-v3-final2.png") — meaningless and noisy. Empty alt="" causes AT to skip the image entirely — correct for decorative images. WCAG 1.1.1 (Level A) mandates alt text.
<figure> + <figcaption> Self-contained content referenced from the main text: images with captions, diagrams, code listings, charts, quoted blocks with attribution. <figure><img src="chart.png" alt="Bar chart of completion rates"><figcaption>Figure 1: Completion rates by week</figcaption></figure>. The <figcaption> can serve as the accessible name: use aria-labelledby pointing to it if the image alt would be redundant. Associates a caption with its image in the accessibility tree. AT users hear both the image description and the caption in context, rather than encountering an orphaned caption that has no obvious connection to its image in the linear reading order.
<ul> / <ol> / <li> <ul> for unordered sets (navigation links, features, bullet points).
<ol> for ordered/sequential content (steps, rankings, numbered instructions). 		Use role="list" on <ul>/<ol> if you apply list-style: none in CSS — Safari VoiceOver removes list semantics when visual bullets are removed. In Tailwind: <ul role="list">. AT announces "list, N items" so users know the total count before navigating items. Without list markup, items are read as a stream of text with no structure. WCAG 1.3.1 (Info and Relationships) requires programmatic structure to match visual structure.
<table> Tabular data — rows and columns with a meaningful relationship between cells. Never for layout. Always include <caption> or aria-label to name the table. Use <th scope="col"> for column headers, <th scope="row"> for row headers. Group rows with <thead>, <tbody>, <tfoot>. AT reads the column and row headers before each data cell: "Status, column 2; Active, row 3; Active". Without <th> and scope, every cell is anonymous data. Complex tables become completely unusable for screen reader users.
<time datetime> Any date, time, or duration that is displayed on the page: "Posted 2 days ago", "Deadline: May 16", "Duration: 1h 30m". <time datetime="2026-05-16">May 16, 2026</time>. The datetime attribute uses machine-readable ISO 8601 format; the element content is human-readable. For durations: datetime="PT1H30M". Search engines, browser extensions, and AT can parse the machine-readable date. "2 days ago" loses meaning when page is cached — the datetime attribute preserves the absolute value. Enables date parsing by calendar apps and voice assistants.
<details> + <summary> Disclosure widgets — expandable FAQ items, "read more" toggles, filter panels, spoiler content. Native alternative to a custom accordion that uses ARIA aria-expanded. <details><summary>What is A11y?</summary> <p>Explanation...</p></details>. The <summary> is the clickable trigger; everything else in <details> is the collapsible panel. No JavaScript required. Full keyboard support built in (Enter or Space to toggle). AT announces "disclosure triangle, collapsed/expanded". Zero ARIA required. The only reason to build a custom accordion is when you need to control animation or coordinate multiple open panels — in that case, add aria-expanded as shown in the ARIA guide.
<abbr title> First use of abbreviations or acronyms on a page: "WAI-ARIA", "WCAG", "A11y", company-specific acronyms. <abbr title="Web Accessibility Initiative – Accessible Rich Internet Applications">WAI-ARIA</abbr>. Only needed on the first use per page. Browser renders as underlined dotted text by default. AT can read out the full expansion to users who do not know the abbreviation. Search engines understand the full term. WCAG 3.1.4 (Abbreviations, Level AAA) recommends this — at AA, use it for any abbreviation that could confuse a new user.

Complete Semantic Page Structure — Angular Component

HTML — Fully semantic Angular 21 page 
<!-- app.html — full semantic skeleton -->

<!-- 1. Skip link — FIRST focusable element -->
<a class="skip-link" href="#main-content">Skip to main content</a>

<!-- 2. Banner landmark — site-wide header -->
<header role="banner">
  <a routerLink="/" aria-label="Angular Todo App — go to home">
    <img src="logo.svg" alt="Angular Todo App" width="120" height="40" />
  </a>

  <!-- 3. Primary navigation landmark -->
  <nav aria-label="Primary navigation">
    <ul role="list">
      @for (link of navLinks(); track link.path) {
        <li><a
          [routerLink]="link.path"
          routerLinkActive="active"
          #rla="routerLinkActive"
          [attr.aria-current]="rla.isActive ? 'page' : null"
        >{{ link.label }}</a></li>
      }
    </ul>
  </nav>
</header>

<!-- 4. Main landmark — unique page content -->
<main id="main-content" tabindex="-1">

  <!-- 5. h1 — one per page, matches route title -->
  <h1>My Todos</h1>

  <!-- 6. Named section becomes a "region" landmark -->
  <section aria-labelledby="filters-heading">
    <h2 id="filters-heading">Filter Todos</h2>

    <!-- 7. fieldset groups related radio buttons -->
    <fieldset>
      <legend>Show</legend>
      <label><input type="radio" name="filter" value="all" checked/> All</label>
      <label><input type="radio" name="filter" value="active"   /> Active</label>
      <label><input type="radio" name="filter" value="done"     /> Done</label>
    </fieldset>
  </section>

  <!-- 8. Article: self-contained todo item -->
  @for (todo of todos(); track todo.id) {
    <article [attr.aria-label]="'Todo: ' + todo.title">
      <h3>{{ todo.title }}</h3>
      <!-- time element with machine-readable datetime -->
      <p>Added <time [attr.datetime]="todo.createdAt">{{ todo.createdAt | date }}</time></p>
      <button type="button" [attr.aria-label]="'Delete todo: ' + todo.title">
        <svg aria-hidden="true" focusable="false">...</svg>
      </button>
    </article>
  }
</main>

<!-- 9. Complementary — sidebar or related content -->
<aside aria-label="Todo statistics">
  <h2>Statistics</h2>
  <p>{{ completedCount() }} of {{ todos().length }} completed</p>
</aside>

<!-- 10. Contentinfo landmark — site-wide footer -->
<footer role="contentinfo">
  <p>© 2026 Angular Todo App</p>
  <nav aria-label="Footer links">
    <a href="/privacy">Privacy Policy</a> ·
    <a href="/terms">Terms of Service</a>
  </nav>
</footer>

5.2 — Angular CDK Accessibility Module

The Angular CDK @angular/cdk/a11y package provides production-ready accessibility primitives that should be the first stop before any custom ARIA solution.

TypeScript 
// app.config.ts — import CDK A11y providers
import { ApplicationConfig } from '@angular/core';
import { A11yModule } from '@angular/cdk/a11y';

// In standalone component imports:
import { FocusTrapFactory, LiveAnnouncer, AriaDescriber }
  from '@angular/cdk/a11y';
TypeScript — Component 
@Component({
  selector: 'app-todo-item',
  standalone: true,
  changeDetection: ChangeDetectionStrategy.OnPush,
  imports: [A11yModule],
  template: `
    <li role="listitem"
        [attr.aria-label]="'Todo: ' + todo().title + (todo().completed ? ', completed' : '')">

      <!-- Checkbox with explicit label association -->
      <input
        type="checkbox"
        [id]="'todo-' + todo().id"
        [checked]="todo().completed"
        (change)="toggle()"
        [attr.aria-describedby]="'todo-desc-' + todo().id" />
      <label [for]="'todo-' + todo().id">{{ todo().title }}</label>

      <!-- Visually hidden description for screen readers -->
      <span [id]="'todo-desc-' + todo().id" class="sr-only">
        {{ todo().completed ? 'Mark as incomplete' : 'Mark as complete' }}
      </span>

      <button
        type="button"
        [attr.aria-label]="'Delete todo: ' + todo().title"
        (click)="delete()">
        <span aria-hidden="true">×</span>
      </button>
    </li>
  `
})
export class TodoItemComponent {
  readonly todo = input.required<Todo>();
  readonly toggled = output<number>();
  readonly deleted  = output<number>();

  private readonly announcer = inject(LiveAnnouncer);

  toggle(): void {
    this.toggled.emit(this.todo().id);
    // Announce state change to screen readers
    this.announcer.announce(
      `Todo "${this.todo().title}" marked as ${this.todo().completed ? 'incomplete' : 'complete'}`
    );
  }

  delete(): void {
    this.announcer.announce(`Todo "${this.todo().title}" deleted`);
    this.deleted.emit(this.todo().id);
  }
}

<form [formGroup]="todoForm"

  </button>

5.4 — Page Title & Router Announcements

Screen readers announce the page <title> on navigation. Without it, users have no indication the route changed in an SPA.

TypeScript — app.routes.ts 
export const routes: Routes = [
  {
    path: '',
    // Angular 14+ built-in title strategy
    title: 'Home — Angular Todo App',
    component: TodoListComponent,
  },
  {
    path: 'about',
    title: 'About — Angular Todo App',
    component: AboutComponent,
  },
];

// For dynamic titles, extend TitleStrategy:
@Injectable({ providedIn: 'root' })
export class A11yTitleStrategy extends TitleStrategy {
  override updateTitle(snapshot: RouterStateSnapshot): void {
    const title = this.buildTitle(snapshot);
    if (title) this.title.setTitle(`${title} — My App`);
  }
}

6

ARIA Patterns & Live Regions

⚠️

Rule 1 of ARIA: Don't use ARIA if you can use native HTML semantics. ARIA only adds meaning — it never changes visual appearance or behaviour. Misused ARIA is worse than no ARIA.

6.1 — ARIA Attributes: When, How & Why

ARIA attributes fall into three categories: roles (what the element is), properties (stable characteristics), and states (dynamic conditions). Use them only when native HTML cannot express the semantics.

Naming & Description Attributes

Attribute When to Use How to Use (Angular 21) Why It Matters / Hierarchy
aria-label The element has no visible text or the visible text is ambiguous. Use on: icon-only buttons, input fields without adjacent labels, landmark regions. Do not use if the element has visible text already — use aria-labelledby instead to avoid the label being out of sync. Static: aria-label="Close dialog"
Dynamic: [attr.aria-label]="'Delete todo: ' + todo().title"
Important: include both the action and the target — "Delete" alone is useless when there are 20 delete buttons on the page. 		AT overrides the element's visible text with the aria-label value. The visible text and aria-label should convey the same intent — discrepancies confuse users who both see and hear the page (speech control users say the visible text to click; if it differs from aria-label, voice activation fails). WCAG 4.1.2 (Name, Role, Value).
aria-labelledby The element's label is already visible on the page as another element. Use on: dialogs (labeled by their heading), sections (labeled by their <h2>), form groups, complex widgets. Preferred over aria-label when visible text exists because it reuses the actual visible text — no duplication. <h2 id="dialog-title">Confirm Delete</h2>
<div role="dialog" aria-labelledby="dialog-title">
Multiple IDs: aria-labelledby="first-name-label last-name-label" (concatenates text of both elements in order). 		aria-labelledby wins over aria-label in the accessible name calculation. Points to another element's id — if the visible heading changes, the accessible name changes automatically. If you use aria-label instead, you must keep both in sync manually.
aria-describedby Supplementary information beyond the accessible name — error messages, hints, help text, character count, format instructions. Not a replacement for aria-labelledby; supplements it. Use on: form inputs (hint / error), dialogs (description paragraph), tooltips. <input id="email" aria-describedby="email-hint email-error">
<p id="email-hint">We'll send confirmation here.</p>
<p id="email-error" role="alert">{{ error() }}</p>
Angular: [attr.aria-describedby]="hasError() ? 'email-error' : 'email-hint'" 		AT reads the name first, then the role, then the description. Screen reader users hear: "Email address, edit text, We'll send confirmation here." The description is read on focus — it is not repeated on every keystroke. Without it, users discover error messages only by tabbing away and back.

State Attributes — Dynamic Conditions

Attribute Values When to Use How to Use (Angular 21) Why
aria-expanded true / false Any custom toggle/disclosure widget: accordion, menu, dropdown, tree node, filter panel. Not needed on <details> — that is native. On the trigger button, not the panel: [attr.aria-expanded]="isOpen()". The button must also have aria-controls="panel-id" to reference the panel. Keep the panel in the DOM with [hidden]="!isOpen()" — @if removes it, breaking the aria-controls reference. AT announces "collapsed" or "expanded" — users know whether activating the button will open or close the panel without guessing from context. Without it, screen reader users must navigate into the panel area to discover whether content is present.
aria-hidden true / remove attribute Decorative content that must be invisible to AT: icon SVGs inside labeled buttons, purely visual spacers, duplicate text. Never on focusable elements. Never on an ancestor of the active focus. <svg aria-hidden="true" focusable="false"> on icons. To remove: [attr.aria-hidden]="shouldHide() ? true : null" — binding to null removes the attribute entirely. Never bind "false" — just omit the attribute. Prevents AT from announcing redundant or confusing content. If a button has aria-label="Delete todo: Buy milk" and an icon with a trash bin inside, the icon must be aria-hidden="true" or AT will read "delete todo buy milk trash graphic" — the icon adds noise, not meaning.
aria-invalid true / false / grammar / spelling After a form control has been touched and fails validation. Do not set on pristine (untouched) fields — pre-marking everything as invalid before the user attempts input is hostile UX. Pair with aria-describedby pointing to the error message. [attr.aria-invalid]="control.invalid && control.touched ? 'true' : null". Combined with error message: [attr.aria-describedby]="control.invalid && control.touched ? 'field-error' : null". Show the error message element only when invalid & touched. AT announces "invalid entry" when the field receives focus, alerting users to the problem before they Tab away. Without it, users submit the form, it fails, and they must hunt for which field is wrong. WCAG 3.3.1 (Error Identification, Level A).
aria-required true Any form field that must be filled in before submission. Use alongside the native required attribute and a visible indicator (asterisk with a legend explaining it). aria-required communicates to AT; native required enables browser validation. <input required aria-required="true" ...>. For the visual indicator: <label>Email <span aria-hidden="true">*</span></label> — hide the asterisk from AT (it will hear "required" from the attribute) and provide a legend: "Fields marked * are required". AT announces "required" when the field is focused — users know before typing, not after the form rejects their submission. The visible asterisk alone is invisible to AT. WCAG 3.3.2 (Labels or Instructions, Level A) requires communicating which fields are required.
aria-disabled true Elements that are visually disabled but should remain focusable and discoverable by keyboard users — e.g., a disabled "Save" button that has a tooltip explaining why it is disabled. Use native disabled for elements that should be completely unreachable. [attr.aria-disabled]="isSaving()". Must also prevent the action in the click handler: (click)="isSaving() ? null : save()". Style with opacity-50 cursor-not-allowed. Do not add native disabled — that removes it from the Tab order. Native disabled removes the element from the Tab order entirely — keyboard users cannot discover it or read its tooltip. aria-disabled="true" keeps focus reachable while announcing "dimmed" (JAWS) or "greyed out" (NVDA), signalling unavailability without hiding the element.
aria-busy true / false A region is loading asynchronously and its content is not yet complete: loading a list, pagination in progress, real-time data refresh. Set to true while loading, remove (or set to false) when done. [attr.aria-busy]="isLoading() ? 'true' : null" on the container element (e.g., the <ul>). Pair with role="status" or a LiveAnnouncer call to announce when loading completes. Tells AT "content in this region is incomplete — do not read it yet." Without it, AT may read partial content and then re-read it after the real data loads, confusing users. With it, AT waits for the region to settle before reading its full content.
aria-current page / step / location / date / time / true The currently active item within a set: current page in nav (page), current step in a wizard (step), current date in a date picker (date). Not a substitute for aria-selected in tabs or listboxes. Angular RouterLinkActive: [attr.aria-current]="rla.isActive ? 'page' : null". Never set both aria-current and class="active" as the only indicator — colour alone violates WCAG 1.4.1. AT announces "current page" next to the active nav link. Without it, keyboard users navigating a long menu list have no way to know which link corresponds to the page they are on. Required for WCAG 2.4.8 (Location, Level AAA) and strongly recommended at AA.

Live Region Attributes

Attribute Values When to Use How to Use Why / Gotchas
aria-live polite / assertive / off polite: non-urgent updates — loading completion, item added/deleted, filter results updated, page number changes.
assertive: urgent, time-sensitive updates — critical errors, session timeout warnings, security alerts.
off (default): suppress announcements for a region that updates frequently as the user types. 		Create the region in the DOM before inserting dynamic content — AT registers regions on page load. <div aria-live="polite" aria-atomic="true" class="sr-only">{{ message() }}</div>. Never use assertive for routine updates — it interrupts whatever AT is currently reading. assertive is like shouting — it cuts off what AT is currently reading. Most updates should be polite. Gotcha: inserting content into a new element (e.g., using @if to add the region dynamically) may not fire the announcement — the region must pre-exist in the DOM.
aria-atomic true / false Use true when the entire region content should be read as one unit after any change, not just the changed node. Use for status messages, counters, compound labels. Use false (default) for live logs where individual new entries should be announced. <div aria-live="polite" aria-atomic="true">{{ count() }} items remaining</div>. With atomic="true", if count() changes, AT reads the whole string "5 items remaining", not just "5". Without aria-atomic="true", AT may only announce the part of the region that changed — so a counter that goes from "4 items remaining" to "5 items remaining" might only announce "5", which is meaningless without context.
aria-relevant additions / removals / text / all Fine-tune what types of DOM changes in the region trigger announcements. Default is additions text. Use removals only for scenarios where removing content is meaningful (e.g., "Error cleared"). Rarely needed — the default works in nearly all cases. aria-relevant="additions removals" — announce both item additions and removals (e.g., for a live log where entries expire and are removed). Avoid aria-relevant="all" — it is noisy and announces attribute changes too. Allows AT to filter noise. Without it, every DOM change in a live region triggers an announcement. For a fast-updating region (live ticker), aria-relevant="additions" prevents AT from repeatedly announcing old items being removed.

Structural ARIA Attributes

Attribute When to Use How to Use Why
role="dialog" A custom modal overlay that is not using the native <dialog> element. Use <dialog> natively whenever possible — it handles focus management and Escape natively. <div role="dialog" aria-modal="true" aria-labelledby="dialog-h" aria-describedby="dialog-desc">. Must use cdkTrapFocus cdkTrapFocusAutoCapture in Angular. Return focus to the trigger element on close. AT announces "dialog" and suppresses the main page content from AT navigation while the dialog is open (with aria-modal="true"). Without aria-modal="true", JAWS and NVDA users can Tab out of the dialog into the main page behind it — a keyboard trap in reverse.
role="alert" Single-use error messages, critical warnings, or important notifications that appear dynamically and require immediate attention. Equivalent to aria-live="assertive" aria-atomic="true" but simpler. <p role="alert">{{ error() }}</p> with @if to show only when an error exists. Angular reactive forms: use inside the form group error display, shown on control.touched && control.invalid. As soon as the element appears in the DOM (or its text changes), AT announces it immediately, interrupting current speech. Use sparingly — like assertive, it interrupts. For non-critical status messages, use role="status" (polite equivalent).
role="status" Non-critical status updates that should be announced politely after AT finishes current speech: "Todo saved", "Filter applied: 3 items", "Your session will expire in 5 minutes" (if non-critical). <div role="status" aria-live="polite" aria-atomic="true" class="sr-only">{{ status() }}</div>. Update the text content — AT announces the full string next time it is idle. Equivalent to aria-live="polite". Choose between role="alert" (urgent, assertive) and role="status" (non-urgent, polite) based on whether the message should interrupt the user. Most app notifications should be role="status".
role="presentation" / role="none" Removing the native semantics of a structural element that is used purely for layout: a <table> used for layout (do not use tables for layout), a <ul> used purely visually with CSS list-style: none in older AT contexts. <ul role="list"> is preferred in modern browsers (Tailwind patterns). <div role="none"> when an intermediate wrapper element would otherwise get an unintended role from its context in a composite widget. Prevents AT from announcing the element's structural semantics. Useful when the HTML structure has to follow a certain nesting pattern for CSS grid/flex but the structure adds confusing AT semantics (e.g., "list 1 item" for a single-item wrapper).

Quick Decision Guide — ARIA vs Native HTML

💡

Ask these questions in order before reaching for an ARIA attribute:

  1. Is there a native HTML element that does this? → Use it. (<button>, <details>, <dialog>, <select>, <label>)
  2. Can I use a native attribute? → Use it. (required, disabled, type, for/id)
  3. Does the element have visible text? → Reference it with aria-labelledby rather than duplicating with aria-label.
  4. Is this a dynamic state change? → Use aria-expanded, aria-invalid, aria-busy, or aria-current as appropriate.
  5. Is this purely decorative? → Use aria-hidden="true" on the element.
  6. Is dynamic content appearing/changing off-screen? → Use aria-live="polite" or Angular CDK LiveAnnouncer.

6.2 — Live Regions — Announcing Dynamic Changes

TypeScript — Using LiveAnnouncer (CDK) 
@Component({
  standalone: true,
  template: `
    <!-- Declarative polite live region -->
    <div aria-live="polite" aria-atomic="true" class="sr-only">
      {{ statusMessage() }}
    </div>

    <!-- assertive for urgent errors only -->
    <div aria-live="assertive" aria-atomic="true" class="sr-only">
      {{ errorMessage() }}
    </div>
  `,
})
export class TodoListComponent {
  private readonly announcer = inject(LiveAnnouncer);

  readonly statusMessage = signal('');
  readonly errorMessage  = signal('');

  async loadTodos(): Promise<void> {
    this.statusMessage.set('Loading todos…');
    try {
      const todos = await firstValueFrom(this.todoService.getAll());
      // Imperative announcement via CDK
      await this.announcer.announce(`${todos.length} todos loaded`, 'polite');
    } catch {
      this.errorMessage.set('Failed to load todos. Please try again.');
    }
  }
}

@Component({

})
export class ConfirmDialogComponent {

  private triggerEl: HTMLElement | null = null;

    this.triggerEl = trigger;

    this.isOpen.set(false);

  }
}

Keyboard & Focus Management

7.1 — Keyboard Accessibility Reference: When, How & Why

Approximately 7% of people with disabilities navigate exclusively by keyboard. Many more use keyboard shortcuts for efficiency. Every interactive element must be reachable and operable with a keyboard alone — this is a WCAG 2.1 AA requirement (SC 2.1.1 Keyboard, SC 2.4.3 Focus Order, SC 2.4.7 Focus Visible).

Pattern When to Use How to Implement Why It Matters
Skip Navigation Link Every page that has a header or navigation before the main content — which is effectively every page. It must be the first focusable element in the page. Visible only on focus using sr-only focus:not-sr-only Tailwind pattern. Points to #main-content (the <main> element's id). The <main> must have tabindex="-1" to be programmatically focusable. Without a skip link, keyboard users must Tab through every header link and nav item on every single page load. A 20-link nav means 20 Tab presses before reaching content — a significant barrier. WCAG 2.4.1 (Bypass Blocks, Level A).
Focus Visible Indicator Every interactive element — buttons, links, inputs, checkboxes, custom widgets. Focus must be visible to keyboard users at all times during keyboard navigation. Use :focus-visible (not :focus) to show the ring only for keyboard users, not mouse clicks. Tailwind: focus-visible:ring-2 focus-visible:ring-indigo-400 focus-visible:ring-offset-2. Never use outline: none on interactive elements — if you must, add an equivalent custom focus style. WCAG 2.4.7 (Focus Visible, Level AA) requires a visible focus indicator. WCAG 2.2 SC 2.4.11 (Focus Appearance) further requires the indicator to have ≥3:1 contrast against its adjacent background. Without it, keyboard users are "navigating blind" — they cannot tell where they are.
Logical Tab Order The reading order of the DOM should match the visual order. If CSS grid or flexbox visually reorders elements, the DOM order must still be logical. Never use positive tabindex values. Keep DOM order = visual order. Use tabindex="0" only for custom interactive elements that need to enter the Tab order. Use tabindex="-1" for elements that need to be programmatically focusable but not in the natural Tab sequence (e.g., modal title). Never use tabindex="1" or higher — it creates a separate Tab sequence that overrides natural flow, causing confusing jumps. WCAG 2.4.3 (Focus Order, Level AA). Illogical Tab order is one of the most common accessibility failures. Screen reader users trust the Tab order to give them a logical flow through interactive elements — surprises and jumps break their mental model of the page.
No Keyboard Traps Every interactive region, widget, and overlay. A keyboard trap occurs when focus enters a region and the user cannot exit using standard keyboard keys. Modals/dialogs: trap intentionally while open (use cdkTrapFocus), but always allow Escape to close and release focus. Custom widgets: ensure the user can always Tab or Escape out. Test by opening every interactive region and pressing Escape and Tab — you must be able to leave. WCAG 2.1.2 (No Keyboard Trap, Level A — the minimum baseline). A keyboard trap renders the entire page unusable for keyboard-only users, who cannot switch to a mouse to escape. This is the most severe keyboard accessibility failure.
Focus Return After Dialog Close Any time an overlay, modal, popover, or dynamic panel is closed. Focus must return to the element that triggered the overlay opening. Store reference before opening: private triggerEl: HTMLElement | null = null; In the open() method: this.triggerEl = document.activeElement as HTMLElement; In the close() method: this.triggerEl?.focus(); When focus is lost (the dialog element is removed from the DOM or hidden), focus typically jumps to the <body> or the top of the page — the keyboard user has completely lost their place. Returning focus to the trigger restores the user's context so they can continue from where they were.
Arrow Key Navigation in Widgets Complex composite widgets where Tab should move between widgets and arrow keys should move within a widget: tabs, radio groups, menubars, listboxes, sliders, date pickers, tree views. Use roving tabindex: only the active item has tabindex="0"; all others have tabindex="-1". Arrow keys update which item has tabindex="0" and call .focus(). Angular CDK: use ActiveDescendantKeyManager or ListKeyManager to manage this automatically. withWrap() enables wrap-around. If every item in a 100-item list has tabindex="0", keyboard users must press Tab 100 times to move past the list. The roving tabindex pattern treats the widget as a single Tab stop and uses arrow keys for internal navigation — matching the keyboard pattern of native OS controls.
Focus Management on Route Change (SPA) Angular SPA — every time RouterLink or router.navigate() loads a new view. Without explicit focus management, focus stays on the link that was clicked — the user is still "on" the old page. On route change, move focus to <main tabindex="-1"> or the page's <h1>. Implement a custom TitleStrategy that updates the page title and announces the new route via LiveAnnouncer: announcer.announce('Navigated to ' + title, 'polite'). See Section 5.4 for the full implementation. In multi-page websites, the browser announces the new page title on navigation. SPAs do not — without explicit management, screen reader users have no indication that a new page loaded. Focus also stays on the old link, so tabbing continues from an unexpected position in the new view.

Testing for Accessibility

Automated tools catch ~30–40% of WCAG issues. The remaining 60–70% require manual and assistive-technology testing. A robust strategy combines all three layers.

The A11y Testing Pyramid

🤖

1. Automated (Static)

Lint rules, build-time checks. Catches missing alt text, invalid roles, wrong heading order.

⚙️

2. Automated (Runtime)

axe-core in Vitest / Cypress. Catches contrast failures, live region issues, ARIA misuse.

⌨️

3. Manual Keyboard

Tab through every interactive element. Verify focus order, focus visible, no traps.

📢

4. Screen Reader

NVDA+Firefox, VoiceOver+Safari, JAWS+Chrome. Real-world AT testing is irreplaceable.

## Accessibility (A11y) Rules — WCAG 2.1 AA Mandatory

### HTML Semantics
- Use semantic HTML landmarks: <header>, <nav>, <main>, <section>, <aside>, <footer>
- Every <section> and <nav> MUST have an aria-label or aria-labelledby
- Never use <div> or <span> as interactive elements — use <button> or <a>
- Every page MUST include a skip-to-content link as the first focusable element

### Forms
- Every <input>, <select>, and <textarea> MUST have an associated <label for="...">
- Required fields MUST use aria-required="true" AND a visible indicator
- Validation errors MUST use role="alert" or aria-live="polite"
- Use [attr.aria-invalid]="control.invalid && control.touched" on inputs

### Buttons & Links
- Icon-only buttons MUST have aria-label describing the action AND the target
  - Pattern: aria-label="Delete todo: {{ todo().title }}"
- Decorative SVGs/icons inside buttons MUST use aria-hidden="true" focusable="false"
- <a> elements MUST have descriptive text — never "click here" or "read more"

### Images
- Informative images: alt="[meaningful description]"
- Decorative images: alt="" aria-hidden="true"
- Angular NgOptimizedImage (ngSrc): always supply width, height, and alt

### ARIA
- Never use ARIA if native HTML semantics already provide the semantics
- aria-label on interactive elements must be unique and descriptive
- Dynamic content changes MUST be announced via LiveAnnouncer or aria-live regions
- Modals MUST use role="dialog" aria-modal="true" aria-labelledby and cdkTrapFocus

### Focus Management
- Never suppress focus outlines — use :focus-visible CSS, not outline: none
- After dialog close, return focus to the triggering element
- Use CDK FocusTrap for all overlays, modals, and drawers
- Positive tabindex values are FORBIDDEN — never use tabindex="1" or higher

### Router
- Every route MUST have a descriptive, unique title property
- On route change, focus MUST be managed — move to main or h1 after navigation

### Signals & Change Detection
- OnPush + signals: ensure aria-live regions update by setting signal values, not
  manipulating the DOM directly — Angular change detection handles the rest

### Colour & Contrast (inform template author)
- Text on coloured backgrounds MUST meet 4.5:1 (normal text) or 3:1 (large text)
- Never communicate state using colour alone — always pair with icon or text
- Focus indicators MUST have 3:1 contrast against their adjacent background

### Testing
- Every component spec MUST include an axe scan: await axe(fixture.nativeElement)
- Cypress E2E specs MUST call cy.injectAxe() + cy.checkA11y() after page load
- Run axe after every user interaction that mutates the DOM significantly

## Accessibility-Driven Tailwind Patterns

### Focus Styles (Mandatory on all interactive elements)
- Use: focus-visible:ring-2 focus-visible:ring-indigo-400
       focus-visible:ring-offset-2 focus-visible:outline-none
- Never use: focus:outline-none alone (removes focus visibility for keyboard users)

### Screen-Reader-Only Utility (must exist in styles.css)
- Class .sr-only hides content visually but keeps it in the AT tree
- Use for: skip links (visible on focus), icon button labels, live region containers
- Never use: hidden or invisible for content that assistive tech must read

### Colour Contrast Guardrails
- Background slate-900 (#0f172a): use text-slate-200 or lighter (≥4.5:1)
- Background slate-800 (#1e293b): use text-slate-100 or lighter
- Avoid text-slate-400 on dark backgrounds for body text — use text-slate-300 minimum
- Status colours: use indigo-400 (not 500) on dark bg, green-400 (not 500), etc.

### Disabled State
- Disabled buttons: add aria-disabled="true" + disabled attribute
- Use: opacity-50 cursor-not-allowed — do NOT rely only on colour change

### Motion
- Respect prefers-reduced-motion:
  motion-safe:transition-all   ← plays on non-reduced-motion
  motion-reduce:transition-none ← disables on reduced-motion

### Icon Buttons — Required Pattern
<button type="button"
        aria-label="[Action]: [Target]"
        class="focus-visible:ring-2 focus-visible:ring-indigo-400 ...">
  <svg aria-hidden="true" focusable="false">...</svg>
</button>

## Accessibility Testing (Mandatory)

### Vitest — axe-core Integration
- Install: npm install --save-dev vitest-axe
- Every component spec file MUST include:

  import { axe, toHaveNoViolations } from 'vitest-axe';
  expect.extend(toHaveNoViolations);

  it('should have no axe violations', async () => {
    fixture.detectChanges();
    const results = await axe(fixture.nativeElement);
    expect(results).toHaveNoViolations();
  });

- Run axe after every significant fixture change (input update, form submit, etc.)
- Do NOT skip axe tests for "simple" components — even <button> can fail

### Cypress — cypress-axe Integration
- Install: npm install --save-dev cypress-axe
- Import in cypress/support/e2e.ts: import 'cypress-axe';
- EVERY e2e feature spec MUST:
  1. Call cy.injectAxe() in beforeEach after cy.visit()
  2. Call cy.checkA11y() with wcag2a + wcag2aa + wcag21aa tags
  3. Re-call cy.checkA11y() after any significant DOM mutation

- Scope scans to components under test:
  cy.checkA11y('[data-cy="todo-list"]')

### Assertions to Always Include
- Checkbox has an associated label via for/id pairing
- Delete/action buttons have aria-label containing the item name
- Error messages appear in role="alert" or aria-live="polite" region
- Focus returns to trigger element after modal/dialog dismissal
- Page title changes on route navigation

# A11y Expert Skill

## Scope
Activate this skill when the user asks about:
- WCAG 2.1 / 2.2 compliance or specific success criteria
- ARIA roles, properties, and states
- Keyboard navigation or focus management
- Screen reader behaviour (NVDA, JAWS, VoiceOver)
- Colour contrast or visual accessibility
- axe-core, cypress-axe, vitest-axe test setup
- Accessibility audits or remediating violations
- Angular CDK A11y module (FocusTrap, LiveAnnouncer, KeyManager)

## Non-Negotiable Rules (always apply)
1. **WCAG 2.1 AA is the minimum bar** — never implement below AA
2. **Semantic HTML first** — ARIA only when native semantics are insufficient
3. **Every interactive element** must be keyboard operable and have a visible focus indicator
4. **Every form control** must have an associated label (for/id or aria-labelledby)
5. **Every icon button** must have aria-label="[Action]: [Target item name]"
6. **Every dynamic update** must be announced to AT (aria-live or LiveAnnouncer)
7. **Every modal** must trap focus and return focus to the trigger on close
8. **axe-core tests are mandatory** — never generate a component without an axe spec

## Angular 21 Accessibility Primitives (prefer these)
| Need                        | Use                                               |
|-----------------------------|---------------------------------------------------|
| Focus trap in modal         | cdkTrapFocus + cdkTrapFocusAutoCapture            |
| Announce dynamic changes    | inject(LiveAnnouncer).announce(msg, 'polite')     |
| Custom keyboard navigation  | ActiveDescendantKeyManager / ListKeyManager       |
| Describe element to AT      | inject(AriaDescriber).describe(el, description)   |
| High-contrast media query   | BreakpointObserver with 'forced-colors: active'   |

## Key WCAG 2.1 AA Success Criteria (quick reference)
- 1.1.1 Non-text Content — alt text on images
- 1.3.1 Info & Relationships — semantic markup
- 1.3.2 Meaningful Sequence — logical DOM order
- 1.4.1 Use of Colour — never colour alone
- 1.4.3 Contrast (Minimum) — 4.5:1 normal text, 3:1 large
- 1.4.4 Resize Text — 200% zoom, no loss of content
- 1.4.10 Reflow — single column at 320px viewport
- 1.4.11 Non-text Contrast — 3:1 for UI components
- 2.1.1 Keyboard — all functions keyboard accessible
- 2.1.2 No Keyboard Trap — always escapable
- 2.4.3 Focus Order — logical, meaningful sequence
- 2.4.6 Headings and Labels — descriptive
- 2.4.7 Focus Visible — visible keyboard focus
- 3.1.1 Language of Page — <html lang="en">
- 3.3.1 Error Identification — described in text
- 3.3.2 Labels or Instructions — instructions before input
- 4.1.2 Name, Role, Value — all UI components
- 4.1.3 Status Messages — programmatically determined

## Testing Mandate
When generating or reviewing any Angular component:
1. Add axe unit test (vitest-axe) to the spec file
2. Verify keyboard operability in manual checklist
3. Suggest cypress-axe scan if no e2e spec exists
4. Call out any colour-only state indicators
5. Verify all dynamic content has a live region or announcer call
