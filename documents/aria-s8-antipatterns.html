8.1

Focus Management Anti-patterns

🚫

Ghost focus is the #1 ARIA bug in production apps: keyboard focus moves to an element but screen readers announce nothing, or the wrong element, because the DOM node has no accessible name and no role.

Anti-pattern #1
Ghost Focus — Focusing a Non-interactive Container
Critical
❌ Wrong
TypeScript — focusElement()
// el is a <div> with no role, no aria-label, tabindex="-1"
this.renderer.setAttribute(el, 'tabindex', '-1');
el.focus();
// Screen reader: silence — or reads the raw text content of the entire div
✅ Fix
TypeScript — correct focus target
// Option A: focus the heading inside the container instead
const heading = container.querySelector('h1, h2, h3') as HTMLElement;
heading?.focus();

// Option B: add role + label to the container if it must receive focus
HTML — labelled container
<div
  role="region"
  aria-labelledby="dialog-heading"
  tabindex="-1"
  #focusTarget>
  <h2 id="dialog-heading">Settings</h2>
</div>
Why: WCAG 2.4.3 Focus Order — focus must land on elements with a meaningful accessible name. WCAG 4.1.2 — interactive controls need name, role, and value.
Anti-pattern #2
Focus Not Returned After Modal Close
Critical
❌ Wrong
TypeScript
closeDialog() {
  this.isOpen.set(false);
  // Focus is lost — lands on body or the last focused element in the stale DOM
}
✅ Fix
TypeScript
private triggerRef = viewChild<ElementRef>('triggerButton');

openDialog() {
  this.returnFocusTo = document.activeElement as HTMLElement;
  this.isOpen.set(true);
}

closeDialog() {
  this.isOpen.set(false);
  this.returnFocusTo?.focus();
}
Why: WCAG 2.4.3 — when a modal is dismissed, focus must return to the element that triggered it so keyboard users know where they are in the page.
Anti-pattern #3
tabindex="0" on Every List Item (Roving Tabindex Misuse)
High
❌ Wrong
HTML — creates excessive tab stops
<ul role="listbox">
  @for (item of items(); track item.id) {
    <li role="option" tabindex="0">{{ item.label }}</li>
  }
</ul>
<!-- 50 items = 50 Tab key stops. Unusable. -->
✅ Fix — Roving Tabindex Pattern
HTML — single tab stop, arrow key navigation
<ul role="listbox" (keydown)="onKeydown($event)">
  @for (item of items(); track item.id) {
    <li
      role="option"
      [tabindex]="item.id === activeId() ? 0 : -1"
      [attr.aria-selected]="item.id === selectedId()">
      {{ item.label }}
    </li>
  }
</ul>
Why: APG Composite Widget Pattern — composite widgets (listbox, grid, tree, tablist) use a single tabindex="0" on the active item. Arrow keys navigate within the widget.
8.2

Role & Semantic Misuse

Anti-pattern #4
role="presentation" / role="none" on Focusable Element
Critical
❌ Wrong
HTML
<button role="none">Save</button>
<!-- Removes the "button" role — announced as plain text. -->
<!-- User cannot tell it's interactive. Keyboard still works. -->
✅ Fix
HTML
<button type="button">Save</button>
<!-- Use role="none" only on decorative, non-focusable elements -->
Why: role="none" on focusable elements is ignored by many AT (the spec says it must be ignored when the element is focusable). However, it creates unpredictable behaviour across AT. Never combine role="none" with focusability.
Anti-pattern #5
Redundant Role on Native Element
Medium
❌ Wrong — noise, not harmful but bad practice
HTML
<button role="button">Save</button>
<a role="link" href="/home">Home</a>
<input role="textbox" type="text" />
✅ Fix — let native semantics do the work
HTML
<button type="button">Save</button>
<a href="/home">Home</a>
<input type="text" />
Why: First rule of ARIA — do not add ARIA if the native element already carries the correct semantics.
Anti-pattern #6
Forbidden Child Role — role="option" Outside role="listbox"
Critical
❌ Wrong — orphaned option role, required context missing
HTML
<div>
  <div role="option">Choice A</div>
  <div role="option">Choice B</div>
</div>
✅ Fix
HTML
<div role="listbox" aria-label="Choose an option">
  <div role="option" aria-selected="false">Choice A</div>
  <div role="option" aria-selected="false">Choice B</div>
</div>
Why: Roles like option, row, tab, menuitem, treeitem have required ownership context. Using them without the parent role breaks AT tree structure.
8.3

Label & Accessible Name Anti-patterns

Anti-pattern #7
Icon Button With No Accessible Name
Critical
❌ Wrong — screen reader announces "button" with no label
HTML
<button type="button">
  <svg aria-hidden="true">...</svg>
</button>
✅ Fix
HTML
<button type="button" aria-label="Delete todo">
  <svg aria-hidden="true" focusable="false">...</svg>
</button>

<!-- Or use visually-hidden text: -->
<button type="button">
  <svg aria-hidden="true" focusable="false">...</svg>
  <span class="sr-only">Delete todo</span>
</button>
Why: WCAG 4.1.2 — all UI components must have a name. WCAG 2.5.3 — label in name (voice control users say "click Delete todo"). Icon-only buttons are one of the most common accessibility failures.
Anti-pattern #8
Placeholder as the Only Label
Critical
❌ Wrong — label disappears on input; fails WCAG 1.3.1
HTML
<input type="text" placeholder="Enter your email" />
✅ Fix
HTML
<label for="email">Email address</label>
<input
  id="email"
  type="email"
  placeholder="you@example.com"
  autocomplete="email"
/>
Why: WCAG 1.3.1 — form inputs require persistent visible labels. Low contrast placeholder text also fails WCAG 1.4.3 in most browser defaults.
Anti-pattern #9
Duplicate, Non-descriptive Link Text
High
❌ Wrong — JAWS links list shows 20× "Read more"
HTML
@for (article of articles(); track article.id) {
  <a [href]="'/articles/' + article.slug">Read more</a>
}
✅ Fix
HTML
@for (article of articles(); track article.id) {
  <a
    [href]="'/articles/' + article.slug"
    [attr.aria-label]="'Read more about ' + article.title">
    Read more
  </a>
}
Why: WCAG 2.4.6 Headings and Labels; WCAG 2.4.9 Link Purpose. Screen reader users navigate by listing all links — identical text makes it impossible to distinguish them.
8.4

Live Region Anti-patterns

Anti-pattern #10
Injecting Live Region and Content Simultaneously
Critical
❌ Wrong — AT cannot register a region that already has content
HTML — broken pattern
<!-- @if creates the element AND inserts content at the same moment -->
@if (announcement()) {
  <div role="status" aria-live="polite">{{ announcement() }}</div>
}
✅ Fix — keep region in DOM, change content only
HTML
<div
  role="status"
  aria-live="polite"
  aria-atomic="true"
  class="sr-only">
  {{ announcement() }}
</div>
<!-- Element always in DOM — empty when no announcement -->
Why: AT registers live regions when the page loads. A region injected via @if is a brand-new DOM node — AT hasn't registered it, so the content is never announced.
Anti-pattern #11
Using aria-live="assertive" for Non-urgent Updates
High
❌ Wrong — interrupts the user constantly
HTML
<div aria-live="assertive">{{ characterCount() }} / 200 characters</div>
✅ Fix
HTML
<div aria-live="polite" aria-atomic="true">
  {{ characterCount() }} / 200 characters
</div>
Why: assertive interrupts whatever the user is listening to. Reserve it for time-critical alerts (session expiry, error that blocks submission). For character counts, search results, status messages — always use polite.
8.5

Keyboard Anti-patterns

Anti-pattern #12
Keyboard Trap (No Escape From Widget)
Critical
❌ Wrong — focus trapped inside a menu with no exit
TypeScript — missing Escape key handler
onMenuKeydown(e: KeyboardEvent) {
  if (e.key === 'ArrowDown') { /* focus next */ }
  if (e.key === 'ArrowUp')   { /* focus prev */ }
  // No Escape handler — user cannot exit the menu!
}
✅ Fix
TypeScript
onMenuKeydown(e: KeyboardEvent) {
  if (e.key === 'ArrowDown') { focusNext(); e.preventDefault(); }
  if (e.key === 'ArrowUp')   { focusPrev(); e.preventDefault(); }
  if (e.key === 'Escape')    { closeMenu(); returnFocusToTrigger(); }
  if (e.key === 'Home')      { focusFirst(); e.preventDefault(); }
  if (e.key === 'End')       { focusLast(); e.preventDefault(); }
  if (e.key === 'Tab')       { closeMenu(); }
}
Why: WCAG 2.1.2 No Keyboard Trap — keyboard users must always be able to leave any component. Escape closes menus, tooltips, comboboxes, and dropdowns.
Anti-pattern #13
Suppressing the Focus Ring (outline: none)
Critical
❌ Wrong — keyboard users cannot see where focus is
CSS
* { outline: none; }
button:focus { outline: none; }
✅ Fix — use :focus-visible, custom style instead of removing
CSS
/* Show focus ring only for keyboard navigation (not mouse) */
:focus { outline: none; }
:focus-visible {
  outline: 2px solid #818cf8;
  outline-offset: 2px;
  border-radius: 4px;
}
Why: WCAG 2.4.11 Focus Appearance (AA in WCAG 2.2) and WCAG 2.4.7 Focus Visible. The CSS :focus-visible pseudo-class only shows the ring for keyboard navigation, not mouse clicks — the correct UX trade-off.
8.6

Angular-Specific Pitfalls

Anti-pattern #14
SSR ID Mismatch Breaks aria-labelledby
Critical
❌ Wrong — random UUID generated differently on server vs client
TypeScript
readonly headingId = `heading-${Math.random()}`;
// Server: "heading-0.123" | Client: "heading-0.456" → hydration mismatch
✅ Fix — use Angular's stable ID
TypeScript
import { inject, ChangeDetectorRef } from '@angular/core';

private static _counter = 0;
readonly headingId = `heading-${++MyComponent._counter}`;
// Counter resets to same sequence on both server and client renders
Why: Angular SSR hydration requires matching IDs between server-rendered HTML and client-hydrated DOM. Mismatched IDs break aria-labelledby and aria-describedby relationships.
Anti-pattern #15
Using @Input() / @Output() Instead of input() / output()
Medium
❌ Wrong — deprecated API, loses signal benefits
TypeScript
import { Input, Output, EventEmitter } from '@angular/core';

@Input() label: string = '';
@Output() selected = new EventEmitter<string>();
✅ Fix — Angular 21 signals API
TypeScript
import { input, output } from '@angular/core';

readonly label = input<string>('');
readonly selected = output<string>();
Why: @Input() and @Output() are deprecated in Angular 17+. Signal-based input() and output() integrate with change detection properly and give type safety on required vs optional inputs.
Anti-pattern #16
DOM Manipulation Inside effect() Outside Angular CD
High
❌ Wrong — direct DOM changes bypass Angular's accessibility tree updates
TypeScript
effect(() => {
  const msg = this.message();
  const el = document.getElementById('announcement');
  if (el) el.textContent = msg;
  // Works visually, but may miss Angular's change detection cycle
});
✅ Fix — bind in template, use CDK LiveAnnouncer
TypeScript
private announcer = inject(LiveAnnouncer);

effect(() => {
  const msg = this.message();
  if (msg) this.announcer.announce(msg, 'polite');
});
Why: Angular CDK's LiveAnnouncer uses an always-registered live region in the DOM. Direct DOM mutation inside effects can race with Angular's rendering pipeline, especially with SSR or ChangeDetectionStrategy.OnPush.
8.7

Quick-Reference Checklist

Use this checklist during code review for every PR that touches accessible UI.

# Check WCAG Category
1 Every icon button has aria-label or visually-hidden text 4.1.2 Labels
2 Every form input has a persistent visible <label> 1.3.1, 3.3.2 Labels
3 Dialogs return focus to trigger on close 2.4.3 Focus
4 Composite widgets use roving tabindex (not tabindex="0" on all items) 2.1.1 Focus
5 All custom keyboard interactions include Escape key handler 2.1.2 Keyboard
6 No outline: none without :focus-visible replacement 2.4.7, 2.4.11 Keyboard
7 Live regions always in DOM — content changed, not element toggled 4.1.3 Live Regions
8 aria-live="assertive" only for time-critical interruptions 4.1.3 Live Regions
9 Angular router navigation announces new page title 2.4.2 Angular
10 No aria-labelledby / aria-describedby IDs generated with Math.random() 4.1.2 Angular / SSR
11 No role="none" on focusable elements 4.1.2 Roles
12 Child roles have required ownership context (option inside listbox, etc.) 4.1.2 Roles
13 No duplicate, non-descriptive link text ("Read more", "Click here") 2.4.6, 2.4.9 Labels
14 All interactive elements are reachable by keyboard Tab and Enter/Space 2.1.1 Keyboard
15 axe-core scan (via @axe-core/playwright) passes with zero critical violations All Testing
✅

Automated baseline: Add @axe-core/angular to your development environment (DevMode only). It runs axe on every change detection cycle and logs violations to the browser console automatically — no manual audit needed during development.
